# 1. おうちノートは何をするアプリか

おうちノートは「家事を採点するアプリ」ではありません。

目的は、家族の毎日の運用で発生する次のことを、言葉と記憶だけに頼らず共有することです。

- 今日だれが何をするか
- いつもと違うことは何か
- 相手にお願いしたことが決まったか
- 実際にはだれが対応したか
- 買い物を誰かがもう対応したか
- 園・学校・予定から準備が必要か
- 返事待ち・確認待ちのことを、必要な日に思い出せるか

「パパが何件、ママが何件」という勝敗や点数を出すためのものではありません。

---

# 2. 基本の考え方

## 2.1 予定の担当と、実際にやった人は別

たとえば「今日はパパがお迎え予定」でも、結果としてママが行くことがあります。

おうちノートでは:

- 予定: パパ
- 実績: ママ

を別々に残します。

過去の実績は、後から担当ルールを変えても書き換えません。

## 2.2 「担当未定」と「誰でもOK」は別

- `担当未定`: まだ責任者を決めていない
- `誰でもOK`: どちらがやってもよいが、やる人は必要なら「自分がやる」でclaimする

誰でもOKを誰かがclaimすると、相手には「対応中」と見えるため、二重対応を減らせます。

## 2.3 お願いは、返事と実行を分ける

「明日のお迎えお願いできる？」に相手が`やる`と返した時点で合意が成立し、実行するTaskができます。

その後の実行状況はTask側で管理します。

お願いの会話と、実際に終わったかは混ぜません。

## 2.4 「待ち」は未完了ではない

問い合わせ済みで返事待ち、予約確認待ちなどは`待ち`にできます。

待ちの間は通常の未完了催促から外れ、次に確認する日になったら再表示します。

## 2.5 「今回は不要」と「できなかった」は別

- 今回は不要: その回だけ、やる必要がなかった
- できなかった: 必要だったが実行できなかった
- 期限終了: 実行期限を過ぎた
- キャンセル: そもそもの実行を取り消した

履歴では区別して残します。

# 3. 毎日の基本動線

## 朝

通常はLINEの朝通知、またはPWAの`今日`を見るだけで始められます。

表示の優先順位は次です。

1. 🔴 まず確認
2. ⏳ 確認日になった待ち事項
3. ⚠️ いつもと違うこと
4. ℹ️ 引き継ぎ・共有
5. ✅ もう済んでいること（自分の行動が変わる場合だけ）
6. 🌅 朝にやること
7. 🌙 夜にやること
8. 💡 余力があれば
9. 相手側の重要な状況

朝通知の標準時刻:

- 平日: 06:30
- 土日・祝日: 09:00

## 日中

普段はアプリを開き続ける必要はありません。

主に次の時だけ操作します。

- 予定が変わったのでお願いする
- 誰でもOKのものを自分がやる
- 完了した
- 返事待ちにした
- 相手から依頼が来た
- 園や予定で新しい重要情報が来た

## 夜

20:30のevening briefを基準に「まだ大事なことだけ」を確認します。

実績入力は次の3段階で負担を選べます。

- `全部やった`
- `大体やった`
- `個別で答える`

`大体やった`は、細かい項目を勝手に完了扱いにせず「概ね対応・詳細未確認」として扱います。

# 4. LINEとPWAの役割

## LINE

日常で最も軽く使う入口です。

固定メニュー:

`今日 | 入力`
`追加 | お願い`
`共有 | その他`

使い分け:

- 今日: 今日の要点
- 入力: まとめて実績入力
- 追加: 予定・タスク・買い物・画像取込
- お願い: 相手への依頼
- 共有: 引き継ぎや情報共有
- その他: カレンダー、イベント、履歴、設定、PWAなど

## PWA

詳細確認や一覧操作に向いています。

- Today
- 履歴
- 買い物
- 予定/カレンダー
- 設定
- 詳細な修正
- conflict/候補確認

LINEとPWAは別々のデータを持たず、同じ家庭状態を表示します。

---

# 5. お願いの使い方

## 軽いお願い

受け取った側の最初の選択肢は:

- `やる`
- `難しい`
- `その他の返答`

その他では:

- 確認してみる
- コメント付きで難しい
- 相談する

などを使えます。

### やる

合意が成立し、必要なら実行Taskが作られます。

### 難しい

元の担当は勝手に変わりません。

### 確認してみる

相手は調整中になります。確認中を何度も通知して急かしません。

### 相談する

「18:30なら行ける」など条件を話し合えます。

具体的な合意候補ができたら、双方が同じ内容を確認して確定します。一方だけが確認した段階では担当は変わりません。

---

# 6. すでに口頭で決めた変更

夫婦で先に話して決まっている場合は`調整済み`として登録できます。

重要な変更の場合、相手には:

`明日のお迎えはママ担当に変更されました（調整済みとして登録） [違う]`

のように出せます。

これは承認依頼ではありません。

もし認識が違えば`違う`から調整に戻します。

---

# 7. 誰でもOK / claim

例:

`牛乳を買う　誰でもOK [自分がやる]`

自分がclaimすると:

`牛乳を買う　パパ対応中`

のような状態になります。

通常のclaimだけで「パパが担当しました」という即時pushはしません。

必要ならclaimした人は`手放す`、もう一方は詳細から`引き継ぐ`を使えます。

---

# 8. 完了・実績入力

## 普通のTask

終わったら完了します。

実際にやった人は、予定担当とは別に残せます。

2人でやった場合も「家庭として2件完了」にはせず、1 Task = 1 completionとして扱います。

## 全部やった

その時間帯で対象となる自分の通常タスクをまとめて完了できます。

待ち・余力タスクなど対象外のものは勝手に完了しません。

## 大体やった

細かい確認を終わらせたい時に使います。

「概ね対応したが、個別の結果は未確認」と記録します。

翌日に残る可能性のある項目がある場合だけ、必要最小限の確認を出します。

## 個別で答える

LINEで例外だけ伝えるか、PWAでまとめて入力できます。

例:

`洗濯はできなかった、着替えはママ`

登録前に解釈結果を確認できます。

---

# 9. 待ちにする

問い合わせや返事待ちなら、Taskを`待ち`にします。

設定できる内容:

- 状況メモ
- 次に確認する日
- 既存の本来期限

例:

`写真館へ問い合わせ済み。返答待ち`
`次に確認: 9/10`
`期限: 9/15`

確認日になると:

`⏳ 写真館の返答を確認する日です`

期限が迫れば:

`🔴 待ち中ですが期限が近いです`

と再浮上します。

---

# 10. 買い物

買い物も担当と実績を分けます。

主な流れ:

1. 買うものを追加
2. `パパ / ママ / 担当未定 / 誰でもOK`を必要に応じて設定
3. 誰でもOKなら`自分がやる`
4. 購入したら購入済みにする
5. 実際に買った人を履歴に残す

二重購入を避けたいものは、相手が行動する前に必要なら中立的に:

`牛乳の買い物は対応済みです`

と通知します。

「ありがとう！ママがやってくれました！」のような採点・称賛pushを標準にはしません。

---

# 11. 引き継ぎ・共有

「相手に知っておいてほしいが、必ず作業を頼むわけではない」内容は`共有`を使います。

例:

- 明日は園の入口が違う
- 病院で薬の時間が変わった
- 荷物は玄関に置いた

作業依頼が必要なら`お願い`、情報だけなら`共有`と使い分けます。

---

# 12. カレンダー / Family Event / Google

Family Eventは家庭内で確認した予定を守るための仕組みです。

重要な原則:

- Family Opsで人が確定した内容を、Google側の変更だけで勝手に上書きしない
- Googleをfollowすると明示した予定だけ、安全な範囲で追従する
- Google削除だけでFamily Eventや準備実績を消さない
- 競合した場合は「今の内容」と「外部から来た変更」を比較して人が決める
- 終日予定を0:00の予定に偽装しない

次期canonical sourceでは安全なownership/競合処理まで準備されていますが、productionのFamily Event Google writer activationは独立gateです。

---

# 13. 園・学校のお知らせ画像

目標フロー:

1. LINEまたはPWAからお知らせ画像を選ぶ
2. 子ども・園/学校を判定
3. 画像に明記された事実を抽出
4. AIの推測は別枠で提案
5. 予定・持ち物・提出物などの候補を確認
6. 人が選んで登録

大事なルール:

- AIだけで予定日や担当を確定しない
- `お知らせに書いてあること`と`AIの提案`を混ぜない
- 別の子・別クラスの情報を家庭の構造化データとして残さない
- URL/QRが怪しい場合は勝手に補完しない
- 元画像を削除しても、確認済みの予定や履歴は残せる

現時点のDD9 sourceはreview-only intake boundaryまでで、外部OCR/AI/Storage adapterはfail-closedです。

---

# 14. 通知の考え方

通知は「相手を評価する」ためではなく「今の行動を変える必要がある時」に使います。

即時通知しやすいもの:

- 返事が必要なお願い
- 重要な担当変更
- 当日の送迎・医療など重要変更
- 薬、送迎、買い物など二重対応を避けたい完了

通常は即時pushしないもの:

- 普通の家事を相手が完了した
- 履歴・分析
- 小さな担当変更
- 待ち期間中の通常日

---

# 15. 履歴

履歴では責任追及ではなく、事実確認をします。

確認できるべき内容:

- 予定していた担当
- 実際にやった人
- 完了日時
- 待ち
- 今回は不要
- できなかった
- 期限終了
- キャンセル
- 修正履歴

将来の担当ルールを変えても過去実績は維持します。

---

# 16. 1人テストモード

妻を本番参加させる前に、1人で「パパ→ママ」「ママ→パパ」の流れを試せる設計です。

テスト表示は必ず`🧪`で区別します。

テスト上のママは本物の妻アカウントではありません。

テストで行った:

- 承諾
- 担当
- 実績
- 合意

を、後から本物の妻の同意として移行しません。

本物の妻が参加した後、必要なら新しい本番依頼として改めて確認します。

production LINE / Google / analyticsへテストデータが漏れないことが設計上の必須条件です。

---

# 17. 妻に最初に伝えるとよい3点

1. **家事を点数化するアプリではない**
   - 今日何をするか、変更があったか、もう誰かが済ませたかを共有するため。

2. **毎日細かく入力しなくてよい**
   - 朝/夜の要点、`全部やった / 大体やった / 個別`で負担を選べる。

3. **お願いが一方的に確定しない**
   - 相手が`やる`と答える、または条件を双方で確認してから担当が変わる。

# 19. 更新ルール

仕様・UIを変更したら:

1. Requirements / accepted designとの整合確認
2. このガイド正本更新
3. `OUCHI_NOTE_USE_CASE_PLAYBOOK.md`更新
4. `OUCHI_NOTE_PARTNER_QUICKSTART.md`更新
5. CURRENT UIで操作確認
6. スクリーンショット更新
7. PDF / HTML再生成

技術実装の都合で利用者向け意味を変えないこと。利用者向け意味を変える場合は先にrequirements/designを更新・reviewすること。
