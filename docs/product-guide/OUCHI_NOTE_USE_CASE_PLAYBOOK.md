# おうちノート — ユースケース別 利用手順書

> 対象: Family Ops / おうちノート
>
> 用途: 家族向け操作説明、受入確認、画面ガイド/PDF作成の元資料

## 0. 読み方

各ユースケースは次の形式です。

- **こんな時**: 使う場面
- **入口**: LINE / PWAのどこから始めるか
- **手順**: 利用者が行う操作
- **こうなる**: 正しい結果
- **注意**: 勝手に変えてはいけないもの、誤操作時の扱い
- **リリース状態**: 現在のsource readiness上の注意

画面位置やボタン名がaccepted designで固定されていない場合、架空のUI位置は書きません。production activation後に実画面で補完します。

# UC-01 はじめて夫婦で使う

**こんな時**  
最初の1人が家庭を作り、パートナーを参加させたい。

**入口**  
PWAの設定 / household onboarding。

**手順**

1. 1人目が家庭を作成する。
2. パートナー招待を作る。
3. 招待リンクをLINE等で共有する。
4. パートナーが自分自身のアカウントでログインする。
5. 招待先の家庭への参加を確認する。
6. 参加後、2人で同じ家庭のToday、お願い、買い物、共有を扱う。

**こうなる**

- 2人は別々の本人identityとして扱われる。
- 同じ家庭状態をLINE/PWAから見る。
- 一方の操作をもう一方のIDで代用しない。

**注意**

- 1人テストで使った`🧪ママ`を、本物の妻アカウントへ変換しない。
- テスト中の合意・承諾は本物のパートナーの同意にならない。

# UC-02 朝、今日の段取りを見る

**こんな時**  
朝、今日の重要事項と自分がやることを短時間で確認したい。

**入口**

- LINE: `今日`
- PWA: Today
- 朝のDailyBrief

**手順**

1. LINEの朝通知または`今日`を開く。
2. 上から「まず確認」を見る。
3. 今日だけ違うことを確認する。
4. 引き継ぎ・共有を見る。
5. すでに対応済みで自分の行動が変わるものを見る。
6. 朝・夜・余力タスクを確認する。

**こうなる**

優先順は原則:

1. 🔴 まず確認
2. ⏳ 確認日になった待ち
3. ⚠️ いつもと違うこと
4. ℹ️ 引き継ぎ・共有
5. ✅ もう済んでいること（自分の負担が減る時だけ）
6. 🌅 朝
7. 🌙 夜
8. 💡 余力
9. 相手側の重要情報

**注意**

- 相手の普通の家事を全部「相手がやった」と並べない。
- waiting中のものを通常未完了として毎朝nagしない。
- 終日予定を`00:00`予定として表示しない。

**標準時刻**

- 平日 06:30
- 土日・祝日 09:00

# UC-03 相手に軽いお願いを送る

**こんな時**  
「明日のお迎えをお願いできる？」のように、相手へ依頼したい。

**入口**  
LINE固定メニュー`お願い`、または対象Task/予定からお願い導線。

**手順**

1. お願いする内容を入力する。
2. 必要なら実行期限と返信期限を確認する。
3. 相手に送る内容を確認する。
4. 送信する。
5. 相手の返事を待つ。

**こうなる**

- 送っただけでは担当は確定変更されない。
- 相手側には最初に`やる / 難しい / その他の返答`が出る。
- 返事が必要な依頼は即時通知対象になり得る。

**注意**

- 返信期限と実行期限は別。
- 古いボタンを後から押しても、現在のAttempt状態を確認して安全に処理する。

---

# UC-04 お願いを「やる」と返す

**こんな時**  
相手から来たお願いをそのまま引き受けられる。

**手順**

1. 依頼メッセージを開く。
2. `やる`を押す。
3. 最新状態が有効ならacceptされる。

**こうなる**

- agreementが成立する。
- 実行が必要ならlinked Taskが作られる。
- 以後の「実際に終わったか」はTask側で管理する。

**注意**

- RequestをacceptしたこととTask完了は別。
- Task完了後に遅れて古いfollow-up操作が来ても、Requestを過去状態へ戻さない。

---

# UC-05 お願いを「難しい」と返す

**こんな時**  
依頼を引き受けられない。

**手順**

1. `難しい`を押す。
2. 必要ならコメントを添える。

**こうなる**

- 依頼のAttemptはdeclinedとして履歴になる。
- 元の担当が勝手に相手へ切り替わらない。

**注意**

- 「難しい」を「今回は不要」やTaskの失敗と混同しない。

---

# UC-06 「確認してみる」で一旦保留する

**こんな時**  
仕事や予定を確認してから答えたい。

**手順**

1. `その他の返答`を開く。
2. `確認してみる`を選ぶ。
3. 自分の予定を確認する。
4. 後から`やる / 難しい / 相談`で返す。

**こうなる**

- requester側には「確認中」と分かる。
- 何度も進捗pushして急かさない。
- 担当はまだ変わらない。

---

# UC-07 条件を相談して決める

**こんな時**  
「18:30なら迎えに行ける」のように条件付きで調整したい。

**手順**

1. `相談する`を選ぶ。
2. 条件を会話する。
3. 具体的な合意候補を確認する。
4. 片方が同じrevisionの条件を確認する。
5. もう片方も同じ条件を確認する。

**こうなる**

- 双方が同じ条件を確認して初めて合意する。
- 一方だけ確認済みなら「相手の確認待ち」。
- その間、現在担当は変わらない。

**注意**

- 条件を編集したら古いconfirmationは無効。
- AIが文章をまとめただけでは誰もconfirmしたことにならない。

---

# UC-08 口頭ですでに決めた担当変更を登録する

**こんな時**  
すでに夫婦で会話して決まっており、アプリだけ後から合わせたい。

**手順**

1. 対象Task/予定の担当変更を開く。
2. `調整済み`として登録する。
3. 変更後担当を確認する。

**こうなる**

重要な変更なら相手側に中立的に:

`明日のお迎えはママ担当に変更されました（調整済みとして登録） [違う]`

のような訂正導線を出せる。

**注意**

- これは承認依頼ではない。
- `違う`が押されたら、既成事実扱いせず調整へ戻る。

# UC-09 「誰でもOK」を自分がやる

**こんな時**  
担当固定するほどではないが、二重対応は避けたい。

**手順**

1. `誰でもOK`のTask/買い物を見る。
2. `自分がやる`を押す。
3. 対応する。
4. 完了/購入済みにする。

**こうなる**

- claim中は「パパ対応中」「ママ対応中」のように見える。
- normal claimだけでは即時pushしない。

**注意**

- `誰でもOK`と`担当未定`は別。
- claimant以外が奪う場合はcurrent claimantを見せてtakeover確認する。
- stale revisionなら現在状態を表示して勝手に上書きしない。

# UC-10 claimを手放す / 引き継ぐ

**手順**

claimした本人:

1. 詳細を開く。
2. `手放す`。

もう一方:

1. 詳細を開く。
2. current claimantを確認。
3. `引き継ぐ`を確定。

**こうなる**

revision-safeにclaimantが更新される。

# UC-11 Taskを普通に完了する

**こんな時**  
担当していた家事・送迎・準備が終わった。

**手順**

1. Taskを開く。
2. 完了する。
3. 必要な場合、実際にやった人を確認する。

**こうなる**

- planned assigneeとactual performerを別に保存する。
- 2人で対応しても1 Taskを2件完了として数えない。
- 履歴へ実績が残る。

**通知**

普通の家事完了では相手へ即時称賛pushしない。

薬・送迎・買い物など二重対応が危険なら:

`朝の薬は対応済みです`

などのneutral messageを出せる。

# UC-12 夜に「全部やった」でまとめて入力する

**手順**

1. LINE`入力`またはevening briefを開く。
2. 対象groupを確認する。
3. `全部やった`。
4. 結果を確認する。

**こうなる**

対象となるrequired/normal active tasksだけをまとめて完了する。

**対象外**

- waiting
- optional/余力
- eligibility外のTask

を勝手に完了しない。

# UC-13 「大体やった」で細かい入力を終わらせる

**こんな時**  
大半は対応したが、1件ずつ正確に入力するほどではない。

**手順**

1. `大体やった`を選ぶ。
2. 必要ならcarryover-sensitiveな項目だけ確認する。

**こうなる**

- group evidenceは「概ね対応・詳細未確認」。
- child Taskを勝手にcompletedにしない。
- 翌日も`未完了`ではなく`前回結果未確認`として扱える。

# UC-14 個別で実績を答える

**手順**

1. `個別で答える`。
2. `LINEで答える`または`PWAでまとめて入力`。
3. LINEなら例外を文章で伝える。
4. 解釈previewを確認。
5. `この内容で登録`または`直す`。

**例**

`洗濯はできなかった、着替えはママ`

**こうなる**

- できなかった
- 実施者変更
- 今回は不要

などを別意味として保存する。

# UC-15 Taskを待ちにする

**こんな時**  
問い合わせ済みで返答待ち、予約確認待ちなど。

**手順**

1. Task詳細から`待ちにする`。
2. waiting_noteを必要なら入力。
3. `次に確認する日`を設定。
4. 保存。

**こうなる**

- 通常未完了一覧/nagから外れる。
- 次回確認日で`確認日です`として再浮上。
- hard dueが近い場合は期限リスクだけ表示可能。

**再開**

`再開する`を明示的に押す。

next-check到来だけで自動active復帰しない。

**こんな時**

**手順**

1. conflict/candidateを開く。
2. CURRENT Family Ops値を見る。
3. Googleからの新しい値を見る。
4. 必要なら差分を確認。

# UC-24 園・学校のお知らせ画像を取り込む

**こんな時**  
Codmonや紙のお知らせのスクリーンショット/写真から予定・準備候補を作りたい。

**目標入口**

- LINE image
- PWA upload

**手順**

1. 解析対象として画像を選ぶ。
2. child / school context候補を確認。
3. 画像に明記されたfactを見る。
4. AI inferenceは別枠で見る。
5. 予定・持ち物・提出物など登録候補を確認。
6. 必要なものだけ人がconfirm。
7. standard Event/Task/Info commandで登録。

**こうなる**

- `source_explicit`と`ai_inference`が区別される。
- 他児童・他クラス情報をdurable structured dataにしない。
- recurrence候補は期間/生成日を確認してから登録。
- 一回だけの変更はrecurrence全体を書き換えない。

**注意**

- AIだけでassignee/date/cancel/Request accept/Google writeをしない。
- URL/QRが不明なら推測生成しない。

**リリース状態**

DD9はsource-side review-only boundaryまで。external OCR/AI/Storage/target adapterは現在fail-closed。

# UC-26 1人で妻役までテストする

**こんな時**  
本物の妻を参加させる前に一連の動きを確認したい。

**手順例**

1. test contextを開始。
2. パパとして`🧪ママ`へRequest。
3. `🧪ママ`としてchecking/consultation/accept。
4. linked test Taskを生成。
5. `🧪ママ`をassignee/claimant/performer/recorderとして操作。
6. Historyで`🧪ママ`表示を確認。
7. test contextをarchive/close。

**こうなる**

- fake auth userを作らない。
- operator本人のuser IDをママの代わりに使わない。
- synthetic messageには必ず`🧪`。
- production LINE outbox / Google / analytics / real consentへ入らない。

**リリース状態**

DD10 source workspace/archive-retryは実装候補。interactive browser/LINE adapter activationは現在fail-closed。

**こうなる**

# UC-29 同じボタンを2回押した / 通信再送された

**こうなる**

- 同じoperation + 同じ内容なら前回結果をreplay可能。
- 同じoperation IDなのに内容が違えばconflict。
- actual、purchase、accept等を二重登録しない。

利用者が「二回押したかも」と不安になっても、二重実行を前提にしない設計。

# 付録B — 結果の意味

| 表示 | 意味 |
| --- | --- |
| 完了 | 必要な対応が完了 |
| 待ち | 外部返答等を待っている。失敗ではない |
| 今回は不要 | このoccurrenceだけ不要だった |
| できなかった | 必要だったが実行できなかった |
| 期限終了 | occurrenceの実行期限が終了 |
| キャンセル | 実行自体を取り消した |
| 前回結果未確認 | 大体やった等で個別結果が確定していない |

# 付録C — 通知されやすさ

| 状況 | 基本方針 |
| --- | --- |
| 新しいお願い・返事必要 | 即時 |
| 重要な担当/送迎/医療変更 | 即時 |
| 普通の家事完了 | 即時pushしない |
| 薬/送迎/買い物等の二重対応防止 | 必要なら中立即時 |
| 小さな担当変更 | 次のbrief |
| waiting通常日 | pushしない |
| waiting確認日 | brief/current |
| waiting hard deadline risk | 必要なら強く表示 |
| 履歴/分析 | proactive pushしない |
