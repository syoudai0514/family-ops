# おうちノート / Family Ops — 独立プロダクト・UXレビュー

- 日付: 2026-09-14
- 対象: CURRENT main (`e0491bc`) の Requirements / design / 実装 / 画面・導線
- 立場: 既存レビュー結果・実装者の自己評価を前提にしない、独立した product / UX 視点
- 種別: **レビューと提案のみ。コード変更は含まない。**

---

## 0. 結論を先に

**おうちノートは「家族の共有ノート」として構想され、「家庭運営ワークフローエンジン」として実装されている。**

思想（README・00_PRODUCT_AND_SCOPE・要望文）は一貫して優れている。
「家庭を仕事のプロジェクト管理にしない」「分類させない」「使うために頑張らせない」。

しかし実装を実際の画面として辿ると、ユーザーは以下を求められる。

- 初回に **8ステップ**の設定ウィザード（曜日×送迎の14セル、夜家事7枠、朝準備）を完了しないとアプリ本体に入れない
- 何か追加するとき、`+` を押すと **10個の選択肢**から「何を追加するか」を自分で分類する
- 「牛乳」を登録するのに **5項目のフォーム**（商品名 / 購入方法 / 担当 / URL / 期限）
- 家事の結果を **7種類**（完了・相手が対応・できなかった・今回は不要・中止・再予定・不明）から選ぶ
- 買い物は **6状態**のライフサイクル（wanted→assigned→ordered→purchased→arrived→cancelled）を進める
- 朝のTodayには最大 **15セクション + 4つの数値タイル + 3つのショートカット**が並ぶ

これは「家庭の頭の中を外に出して楽にする」ではなく、
**「家庭の頭の中を正確にモデリングして、その正確さの維持コストをユーザーに払わせる」**になっている。

差は機能の欠落ではない。**削る判断が一度も行われていない**ことにある。
仕様レビューが5ラウンド回っている一方で、「この入口は要らないのでは」という引き算のレビューが1度もない。

以下、影響の大きい順に。

---

## 1. 今はじめて見た印象

ドキュメントを読んだ時点での期待値は非常に高い。
「言いづらいお願い」「引き継ぎ」「予定変更」まで射程に入れているプロダクトは、
家事ToDoアプリとは明確に別物で、実際に家庭で起きている問題を正しく捉えている。

そのうえで、リポジトリを開いて最初に受けた印象は3つ。

1. **設計の質が高い。** 特に `planned_assignee` と `actual actor` の分離、
   採点しない方針、原文を相手に見せない方針、`今回は不要` と `できなかった` を潰さない方針。
   ここは家庭向けプロダクトとして稀に見る良い判断で、他社が真似できない部分。

2. **その質の高さが、そのままユーザーに露出している。**
   設計上の厳密な区別（7種類の結果、6状態の買い物、`待ち` 状態、
   revision/CAS、重複判定の3択）が、ほぼ1対1でUIの選択肢になっている。
   内部モデルの正確さと、画面に出す選択肢の数は、本来まったく別の判断のはず。

3. **画面の枚数が「家族の共有ノート」の規模を超えている。**
   ルート27本、Edge Function 約100本、設定メニュー10項目。
   そのうち2つ（`削除・中止・結果の違い` / `LINE / PWA 入力対応表`）は
   機能ではなく **「このアプリの概念の説明ページ」**。
   説明ページが必要になっている時点で、概念モデルがユーザーに対して重すぎる。

## 2. 一番良いところ（残すべき理由つき）

### 2.1 「採点しない」という思想が、データモデルまで貫通している

- `planned_assignee` と `actual contributor` が別
- 勝率・ポイント・ランキングを **仕様として禁止**（00_PRODUCT_AND_SCOPE §3, 02_UX §8）
- 相手の完了を `ママがやってくれました` ではなく `水着セットは準備済み` と中立に出す（04 §16.2）
- 通常の家事完了は相手にpushしない

**これは本気で守るべき。** 夫婦で家事アプリが失敗する最大の理由は「見える化が査定になる」ことで、
このプロダクトはそれを思想レベルでもスキーマレベルでも避けている。
競合優位になり得る数少ない部分なので、以降どんな簡素化をしても、ここだけは削ってはいけない。

### 2.2 「原文を相手に見せない」＋「AIは事実を変えない」

お願いのStep1（自分用の生の文章）をrecipientに一切見せず、
AIが整形した共有文だけを送る。しかも AI が事実・数量・期限・依頼対象を変えたら
invariant チェックで弾き、失敗時に raw text へフォールバックしない（`_shared/gemini.ts`）。

**これは「言いづらいお願い」というこのプロダクト固有の価値の中核**で、
かつ技術的にもきちんと実装されている（30以上のgolden fixture）。
ここを起点に製品を組み立て直す価値がある。

### 2.3 LINEの `大体やった`

`全部やった / 大体やった / 個別で答える` のうち、`大体やった` は秀逸。

> 夜の家事は「概ね対応・詳細未確認」として記録しました。細かい入力はもう求めません。

翌日は `未完了` ではなく `前回結果未確認` と表示する。
**「入力を諦めてもいい」という逃げ道を、罪悪感なしに、データの正確さも壊さずに用意している。**
家庭向けプロダクトでこの発想に到達しているのは相当良い。これも残すべき。

### 2.4 週末の `誰でもOK` とclaim

土日に送迎担当がいないとき、役割由来の家事を「担当未定（要確認）」にせず
`誰でもOK` にして、`自分がやる` で取る。取り合いを防ぐためtakeoverは
現在の担当者を再読して見せてから確定する（04 §14.1, §15）。

**土日の家庭は平日と構造が違う、という認識を持っている製品は少ない。** 良い。

### 2.5 LINE側の多意図プレビューは、思想通りに動いている

`明日水遊び。水着は自分で準備。牛乳買う。金曜迎えお願い。今日は掃除機やった。`
→ 1回のプレビューに5件まとめて表示 → 1タップで登録。
確認は2往復。**ここだけは要望文の理想にほぼ到達している。**

## 3. 一番もったいないところ

**LINEで実現できている「分類させない1往復」の体験が、PWAには一切移植されていない。**

同じ「牛乳買っといて」を入れるのに:

| | LINE | PWA |
|---|---|---|
| 操作 | 文章を1通送る → プレビュー → `登録` | `+` → 10択から`✨ おうちコンシェルジュ`を選ぶ → 入力画面で文章 → `AIで整理` → 候補画面でチェック → `選択した内容をまとめて登録` → 確認画面 → `登録する` → `元の画面へ戻る` |
| 画面 | 1 | 4 |
| タップ | 2 | 6〜7 |

しかも PWA の入口名が `✨ おうちコンシェルジュ` という**機能名**で、
10択リストの1行目に他の9個と並列に置かれている。
ユーザーから見れば「AIっぽい特別なモード」であって、「普通の入口」ではない。

**要望文にある「AI機能を使うという感覚を強くしたくない」と、実装は正反対になっている。**

さらに PWA の concierge は **一発変換専用で、会話ができない**。

- 「さっきの時間だけ変えて」→ 前の入力の記憶がないので不可（LINEにはある）
- 「今日なんか予定あったっけ？」→ 通ることは通るが、返ってくる画面の見出しが
  **`登録する内容はありません`**。質問に答えたのに失敗メッセージに見える。
- 「妻にどう言えば角立たない？」→ PWAには相談の受け口自体がない

結果として、**PWAはLINEの劣化版の入力フォーム集**になっている。
本来PWAは画面が広く、履歴もあり、まとめて操作できる — LINEより有利な条件が揃っているのに、
一番効く体験（自然文1発）だけがLINE専用になっている。

## 4. 最も優先して変えるべきこと（影響度順）

### P1. PWAの `+` から「分類」をなくす

**現状:** `+` → モーダルに10択
（コンシェルジュ / 単発ToDo / イベント・予定 / お願い / 買い物 / 引き継ぎ / 画像から取り込む / 定例 / 朝準備 / 予定外実績）

要望文の
> お願い・共有・予定・買い物等をユーザーが意識して分類しなくて済むか

に対して、**現状は10個の分類を先に要求している。** 思想と実装が最も鋭くズレている箇所。

**提案:** `+` を押したら、いきなり入力欄が出る。それだけ。

```
┌────────────────────────┐
│  何でもどうぞ                        │
│  ┌──────────────────┐  │
│  │ 明日迎えお願い。あと牛乳も  │  │
│  └──────────────────┘  │
│                    🎙      ▶  │
└────────────────────────┘
```

分類は結果のプレビューで示せばよく、入力前に問う必要がない。
`予定 / ToDo / 買い物 / 共有 / お願い / 実績` のチップは現在 concierge 画面に
**表示専用のラベル**として置かれているが、これも「6種類あるぞ」と身構えさせるだけなので不要。

10択のうち `定例を追加` `朝準備を編集` は明らかに設定であって「追加」ではない。設定へ移すべき。
`画像から取り込む` は「入力欄の隣のカメラアイコン」で足りる。
`予定外実績` は `掃除機かけた` と書けば実績として解釈されるべきもので、専用入口は要らない。

**残すべき入口は `+`（自然文）ただ1つ。** これだけで9画面ぶんの導線が消える。

### P2. PWAの確認を4画面から1画面にする

現状 `concierge → results → confirm → 完了` の3画面で、
results と confirm は **ほぼ同じ候補リストを2回見せている**。
confirm 画面の存在理由は「登録を押すまで作らない」という安全境界の可視化だが、
その境界は results 画面の `登録` ボタンでも同じように担保できる。

**提案:** 入力欄の直下にプレビューをインライン展開し、その場で `登録`。画面遷移ゼロ。

```
明日迎えお願い。あと牛乳も
─────────────────────
🙏 お願い   明日のお迎え → ママ    ✎
🛒 買い物   牛乳                  ✎
─────────────────────
        [ 登録する ]
```

重複確認（既存を使う/更新/別物）も、**該当したときだけ**その行に出す。
今は confirm 画面に常設セクションとして構えているので、
何もなくても「重複を気にしないといけないアプリ」に見えてしまう。

### P3. Today を「ダッシュボード」から「次に何をすべきか」に戻す

02_UX §1 は自ら宣言している:

> Todayはdashboardではなく「次に何をすべきか」。

実装 (`Today.tsx`) の朝の画面を上から数えると:

1. ヘッダ + `＋ 追加`
2. ショートカット3個（入力 / お願い / 共有）
3. **数値タイル4個**（要対応 n / 残り n / 待ち n / 明日影響 n）
4. まず確認
5. いつもと違うこと
6. 昨夜からの持ち越し
7. 未読の引き継ぎ
8. 対応済み
9. 待ち・確認
10. 今日の入力
11. 朝やること
12. このあと
13. 相手の今日
14. 今日の予定
15. 余裕があれば
16. 明日の見通し
17. 買い物（折りたたみ）
18. 明日の準備カード

**これは定義上ダッシュボードで、しかも計器の多い方のダッシュボード。**

特に3の数値タイルは害が大きい。`要対応 2 / 残り 7 / 待ち 1 / 明日影響 3` は
**家庭の状態を4つのKPIに要約した表示**で、要望文の「家庭を仕事のプロジェクト管理のようにしない」に
真正面から反する。朝6:30にこれを見る体験は、出社してダッシュボードを開くのと同じ。

**提案:**

- **数値タイル4個は削除。** 数はセクション見出しの `n件` に既にある。
- Todayの第一画面は **1画面スクロールなしで収まる量**に固定する。
  - 上: 今どうしても判断が要るもの（0件なら出さない）
  - 中: **次の1件**（`17:30 お迎え` のような具体）
  - 下: `今日やること n件 ▾`（畳んだ状態）
- それ以外（対応済み・相手の今日・余裕があれば・買い物・明日の見通し）は
  **既定で畳む or Todayから外す**。
- `もう済んでいること` は「自分の負担が減ったもの」限定という良い仕様があるのに、
  朝の3番目に常設セクションとして出てしまっている。1行のインラインバッジで十分。

朝に必要なのは「今日これだけ気をつけて」の1〜3行であって、家庭の完全な状態表ではない。

### P4. LINEの朝ブリーフが最大12セクションの壁になっている

`fn_render_daily_brief_text_v3` が生成する朝メッセージは、
**単一のプレーンテキストに最大12個の見出し**を積み、5000文字で切る。

```
朝のおうちノート

まず確認
・…
いつもと違うこと
・…
引き継ぎ・共有
・パパ → 家族｜共有｜確認待ち（LINEで「共有確認」）
  …
もう済んでいる
・…
待ち・確認
・…
今日の予定
・…
朝やること
・…
日中にやること
・…
夜にやること
・…
余力があれば
・…
相手の今日
・残り 3件・待ち 1件・完了 2件
明日の準備・変更
・…
まとめ入力
・未確認 4件
```

スマホのLINEで朝6:30にこれが届く。**読まれない。**
読まれないと「まず確認」に入れた本当に重要な1行も一緒に埋もれる。
セクションを増やすほど、最上段の緊急項目の価値が下がるという逆説が起きている。

04_LINE_PWA §4 は「own tasksをPWAに隠して騒音を解決するな」と書いていて、その原則自体は正しい。
だが**「全部本文に出す」と「全部同じ濃度で出す」は別**であり、現在は後者になっている。

**提案（朝のLINE）:**

```
おはようございます。今日はこれだけ。

⚠️ 16:30のお迎え、ママの会議と重なっています
   [パパが行く] [ママのまま] [相談する]

🌅 朝: 保育園バッグ・水筒・連絡帳
🌙 夜: 洗濯・お風呂

[今日の詳細] [入力]
```

- 本文に出すのは **例外 + 自分の担当（時間帯ごとに1行に圧縮）** だけ
- `もう済んでいる` `相手の今日` `待ち` `余力があれば` `まとめ入力` は
  **詳細を開いたときだけ**。朝の本文からは外す
- `引き継ぎ・共有` の現在のフォーマット
  （`パパ → 家族｜共有｜確認待ち（LINEで「共有確認」）`）は
  メタデータが本文より多い。**`パパ: 今朝は朝食少なめでした` だけでいい。**

### P5. 初期設定8ステップが、ほぼ確実にここで人が脱落する

`HouseholdGate.tsx` の gating:

1. 家庭を作る
2. パートナーを招待（`初期設定 2 / 8`）
3. **送り・お迎えの曜日設定**（2種 × 7曜日 = 14セル、各セルに チェック + 担当select + 時刻input）
4. 夜の定例家事（7コード必須）
5. 朝の準備
6. LINE / カレンダー連携
7. 通知タイミング（8項目）
8. 週プレビュー

**アプリの中身を1度も見ないうちに、これを全部埋めないと `ready` にならない。**
しかもステップ表示が `2 / 8` と `4 / 7` `5 / 7` `6 / 7` `7 / 7` で不整合になっており、
ユーザーは自分が全体のどこにいるかも分からない。

これは家族向けプロダクトとして致命的で、理由は2つ。

- **配偶者が絶対に付き合わない。** 導入する側（おそらく1人）が突破できても、
  招待された側が最初に見るのが設定ウィザードなら、その時点で終わる。
- **設定に必要な知識を、使う前には持っていない。**
  「木曜の送りは誰？」は生活の中では自明だが、14マスのグリッドを前にすると
  「例外の週はどうする」「時間は毎回違う」と考え込んでしまう。

**提案:**

- **ゲートを全部外す。** サインイン直後に Today を出す（空でよい）。
- 送迎の担当は **初回の「今日」を作るときに、その日ぶんだけ聞く**。
  「今日のお迎えは誰？ [パパ] [ママ] [いない]」
- 2週間ぶん答えたらパターンが立つので、そこで初めて
  「木曜はいつもママみたいですね。定例にしますか？ [はい] [今のままでいい]」と提案する。
  **設定を、前払いの作業から、後払いの提案に変える。**
- LINE連携だけは価値が大きいので、Todayの上に1枚バナーとして残す（スキップ可能）。

### P6. 家事の結果7種・買い物6状態は、家庭のモデルとして過剰

**結果7種:** `完了 / 相手が対応 / できなかった / 今回は不要 / 中止 / 再予定 / 不明`

区別自体は正しい（`今回は不要` と `できなかった` を潰さない判断は良い）。
問題は、**その7択を毎晩ユーザーに見せていること。**

夜の `その他の結果` を開くと、7つのボタンと日付ピッカーが1つ出る。
洗濯物をたたまなかった、というだけの出来事に対して、
`できなかった` か `今回は不要` か `中止` か `再予定` かを判断させられる。
これは家庭の会話にない粒度で、しかも間違えると履歴が汚れるという緊張がある。

**提案:**

- 既定は **`完了` と `やらなかった` の2択**（＋ `相手がやった`）。
- `やらなかった` を押したあと、**必要なときだけ** 1行で聞く:
  「今日は要らなかった？ [うん] [できなかっただけ]」
  答えなければ `unknown` のままで、それでいい（`大体やった` の思想と同じ）。
- `中止` `再予定` は結果ではなく**予定の編集**なので、結果の選択肢から外し、
  項目の `•••` に置く。

**買い物6状態:** `wanted / assigned / ordered / purchased / arrived / cancelled`

さらに追加フォームが 商品名 / 購入方法 / 担当 / URL / 期限 の5項目。
**「牛乳」に対してこれは重い。**

`ordered → arrived` はネット注文には意味があるが、
牛乳・おむつ・トイレットペーパーという実際の9割には `ある / 買った` しかない。

**提案:**

- 入力は **タイトルだけ**。他は全部オプションで、URLを貼ったときだけ
  「ネット注文ですね」と `ordered/arrived` の2状態が現れる。
- 既定の状態は **`ほしい` → `買った`** の2つ。
- `誰でもOK` のclaimは良い仕組みだが、買い物リストの既定は「誰でもOK」でよく、
  `担当: 未定 / 誰でもOK / 担当者を指定` の3択を毎回聞く必要はない。

### P7. LINE無料枠200通と、定例通知の設計が構造的に衝突している

平日の定例スケジュール（17_ROUTINE_LINE_AUTOMATION）:

| 時刻 | 宛先 | 通数 |
|---|---|---|
| 07:00 今日の担当 | 大人2人 | 2 |
| 07:00 送り担当チェック | 1人 | 1 |
| 08:30 送り担当check-in | 1人 | 1 |
| 16:00 迎え担当チェック | 1人 | 1 |
| 20:00 迎え担当外の夜チェック | 1人 | 1 |
| 20:30 迎え担当check-in | 1人 | 1 |
| 22:00 迎え担当外check-in | 1人 | 1 |

平日で最大8通/日、土日祝は4通/日。
月平均（平日22日 × 6〜8 + 休日8日 × 4）で **約165〜210通**。

**`soft_budget=180` に、定例通知だけで到達する。**

その結果:

- 月の後半、**soft budget超えで check-in reminder が LINE から in-app へフォールバック**
- hard limit (200) 到達後は **すべての push が止まる**
- 残る唯一の経路は「in-app通知」

しかし **PWAにWeb Pushは実装されていない**
（`PushManager` / `Notification.requestPermission` / VAPID のコードがリポジトリ内に存在しない）。

つまり **in-appフォールバック = 「ユーザーが自分でアプリを開かないと何も届かない」**。

そして、押し出される優先度の低いものが定例リマインダーなのに対し、
**押し出されずに枠を食い続けるのも定例リマインダー**という構造になっている。
本当に届くべき「お迎え変わってほしい」「今日のお迎えが重複してる」が、
毎日の定例チェックインに枠を食われて届かなくなる。

**これはUXの問題ではなく、プロダクトの前提が壊れている箇所。** 対処は3つのどれか。

1. **定例通知を大幅に減らす。** 07:00の1通に集約し、
   08:30 / 20:30 / 22:00 の check-in reminder を **既定オフ**にする
   （04 §7 が既に「残件がなければ短くしてよい」と言っているので、思想とは矛盾しない）。
   これで平日3通/日・月90通程度になり、100通ぶんが本当の連絡用に空く。
2. **check-in を push ではなく reply で回収する。**
   ユーザーが何か話しかけたときの reply token はquota非対象なので、
   「ついでに聞く」形にすれば0通で済む。
3. **PWAにWeb Pushを入れる。** 定例はPWA push、LINEは人対人の連絡だけ、と役割を分ける。

個人的には **1 + 3 の組み合わせ**を推す。理由は次節。

### P8. 設定に「概念の説明ページ」が2つある

- `削除・中止・結果の違い` — 「消す前に、何を直したい？」
- `LINE / PWA 入力対応表` — 「LINEの固定入口6つと、個別結果を答える場所」

どちらも真面目に書かれた良い文章だが、**これらが必要になっている事実そのものが症状**。

- 前者が必要 = **削除と結果の区別がUIから自明でない**
- 後者が必要 = **LINEとPWAの役割分担がユーザーに伝わっていない**

説明ページを足すのではなく、**説明が不要になるまでUIを削る**のが正しい対処。
P6（結果2択化）とP1（入口1つ化）が通れば、この2ページは自然に不要になる。

同様に、設定メニュー10項目のうち
`家庭内用語` `「誰でもOK」の対応状況` `Google予定の変更確認` `🧪 1人テストモード` は
**運用・デバッグ用の画面がユーザー設定に混ざっている**。
特に `🧪 1人テストモード` が一般ユーザーの設定画面に出ているのは整理されていない。

## 5. LINEとPWAの役割分担 — 今の方向は「ほぼ正しいが、逆の部分がある」

現在の方向:

- LINE = 日常の入力・確認・依頼の主入口
- PWA = Today・詳細・設定・履歴・まとめて操作

**この分担自体は正しい。** 家庭の入力は「思いついた瞬間」に起きるもので、
その瞬間に開いているのはLINEであってPWAではない。

ただし**実装は、この分担を活かしきれていない**。

### 5.1 LINEのリッチメニューが公開されていない

04 §12 は固定メニュー `今日 | 入力 | 追加 | お願い | 共有 | その他` を定義している。
しかしリポジトリ全体に **richmenu のAPI呼び出しが存在しない**
（`buildLineMenuFlex` にコメントで
`source/builder-only until provider menu publication is explicitly approved` と明記されている）。

つまり現状、ユーザーがこの6入口に到達するには
**「メニュー」と打つか、「できること教えて」と打つ**必要がある。

**LINEの最大の資産は、チャット下部に常駐するリッチメニューである。**
何もしなくても常に画面にあり、押せば動く。これを使っていないのは大きな機会損失で、
しかも実装コストは低い（Messaging APIのrichmenu登録1回）。

**提案:** 6ボタンではなく **3ボタン**でリッチメニューを公開する。

```
┌─────────┬─────────┬─────────┐
│  今日     │  入力     │  アプリ    │
└─────────┴─────────┴─────────┘
```

`追加` `お願い` `共有` はメニューに要らない。**全部「そのまま喋る」で済むから**であり、
メニューに置くと「メニューから選んで分類する」導線を復活させてしまう。

### 5.2 PWAは「まとめて見る場所」なのに、Todayが「まとめて見る画面」になっていない

役割分担どおりなら、PWAのTodayは
「LINEで断片的にやり取りした結果が、ちゃんと収まって見える場所」であるべき。
ところが現状のTodayは、LINEの朝ブリーフとほぼ同じ情報を、同じ順番で、
同じ密度で再掲している（設計上「同じDailyBriefを使う」ため）。

**同じread modelを使うのは正しい。同じ見せ方をするのは間違い。**

- LINE = 通知チャネル → **押し出す情報。少ないほどよい。**
- PWA = 参照チャネル → **引き出す情報。構造化されているほどよい。**

PWAで本当に欲しいのは、Todayの縦積みではなく**「今週の見取り図」**。
月・週ビューがボトムナビの5枠中2枠を占めているのに、
それが「今週わが家がどうなっているか」を答える画面になっていない。

### 5.3 ボトムナビが、このプロダクトの価値を反映していない

現状: `今日 | 週 | 月 | 買い物 | 履歴 | ＋`

- **5枠中2枠がカレンダービュー。** 週と月は、家庭の日常利用で1日1回も開かない。
- 一方、このプロダクト固有の価値である **`お願い` と `共有` はナビに存在しない**
  （Today上部のショートカットボタンからしか行けない）。
- `履歴` が常設。家庭で履歴を毎日見る人はいない（見る人がいたらそれは査定であり、思想に反する）。

**提案:** `今日 | 家族 | ＋ | 買い物 | 設定` の4+1。

- `家族` = お願い・共有・引き継ぎ・相手の状況をまとめた1画面
  （このプロダクトが他と違う部分を、初めてナビの一等地に置く）
- 週/月は Today からのリンクと `家族` の中へ
- `履歴` は Today の最下部リンクか設定へ

## 6. AIをどこにどう置くか

### 6.1 現状の評価

**良い点:**

- 安全境界の考え方は完全に正しい。
  「AIに相談しているだけなのに勝手に家族へ送らない」を、
  決定論的ガード + source-span検証 + モデル出力を権威にしない、の3重で守っている。
  `妻にどう言えば角立たない？` `これはまだ送らないで` を業務アクションにしない、
  という要件を明示的にテストしている（04 §26.2）。
  **この方針は絶対に維持すべき。**

**問題点:**

**(a) 実装手段が正規表現の巨大な階段になっている。**

`lineConversation.ts` は「相談かお願いか」を数十本の正規表現で判定している。
`AI-NL-QUALITY-RESULTS` によれば、この判定の初期ベースラインは **36件中5件しか通らなかった**
（31件が「相談→家族へのアクション」への誤変換）。
それを正規表現の追加で 36/36 まで持ち上げ、最終ホールドアウト12件が12/12。

この直し方は、**新しい言い回しが来るたびに壊れる**。
実際の家庭の日本語は、テストコーパスよりはるかに多様で、崩れていて、文脈依存。
そして失敗の代償が非対称:

- 相談→アクションに誤判定 = **危険**（勝手に配偶者へ送られる。最も避けたいこと）
- アクション→相談に誤判定 = **摩擦**（「これは私への相談ですか？」と毎回聞かれる）

現状の設計だと、安全側に倒すほど摩擦が増え、
`これお願いできる？` のような普通の発話が
毎回 `これは私への相談ですか？それとも家族へのお願いですか？` で止まる。
**「使うために頑張るアプリ」に戻ってしまう。**

**(b) 会話アシスタントが、家庭について何も知らない。**

`buildAssistantConversationReply(text)` は **単一メッセージのみ**を受け取る。
会話履歴なし、家庭の予定なし、タスクなし、家族の名前なし。

だから `妻にどう言えば角立たない？` に対して返るのは、
汎用的な「状況 → お願い → 難しければ言ってね の順がいいです」という一般論。

**これは要望文の理想の真逆。** 本来欲しいのは:

> 「今週パパが3日連続でお迎えしてるので、
>   『今週ずっと行ってもらってて助かってる。金曜だけ代わってもらえる？』
>   みたいに、状況の共有から入ると角が立たないと思います。」

家庭の実データを持っているのがこのプロダクトの唯一の強みなのに、
**相談のときだけそれを使っていない。**

**(c) PWAにAIの相談入口がない。**

「言いづらいお願い」を考えたいとき、LINEで打つのは相手のトーク画面と隣り合っていて心理的に近い。
落ち着いて言葉を選びたいときこそPWAの広い画面が向いているのに、
PWAのAIは「一発で候補に変換する機械」しかない。

### 6.2 提案: AIを「機能」ではなく「入力欄そのもの」にする

**原則: AIの入口を作らない。入口を全部AIにする。**

```
現状:   [+] → [10択] → [✨ おうちコンシェルジュ] → 入力欄
提案:   [+] → 入力欄（これがAI）
```

ユーザーは「AIを使う」と意識しない。**ただ書く。**
おうちノートが意味を理解して、必要な形にする。要望文の理想そのもの。

**置き場所は3つだけ:**

1. **LINEのトーク画面そのもの**（既にほぼできている。リッチメニューを公開すれば完成）
2. **PWAの `+`**（1画面・インラインプレビュー。P1/P2）
3. **Todayの各項目の `•••` から出る「これ、どう言えばいい？」**
   — お願いを作る文脈にAIを埋め込む。単独の「AI相談」メニューは作らない。

**チャットUIに寄せるべきか？** — **PWAは寄せない方がいい。**

理由:
- チャットUIは履歴が縦に流れる = **過去に何を頼んだかが分かりにくくなる**。
  「共有ノート」というプロダクトの本質と合わない。
- LINEが既にチャットなので、PWAで同じことをすると**2つのチャット履歴が分裂する**。
  「さっき頼んだのどっちだっけ」が起きる。
- PWAの価値は「状態が構造化されて見えること」。チャットはそれを壊す。

**代わりに: 入力欄はチャットのように賢く、結果はリストとして構造化して見せる。**
入力は会話的、出力は構造的。これが「共有ノート」の正しい形。

ただし**LINE側は完全にチャットでよい**。というより、LINEがチャットであることが
このプロダクト最大の資産で、PWAはそれを真似るべきではない。

### 6.3 提案: 安全境界を「判定」から「設計」に移す

正規表現で「相談かお願いか」を当てにいくのをやめ、
**間違えても危険にならない構造**にする。

**キーになる不変条件は1つだけ:**

> **どんな入力からも、ユーザーが明示的に1タップするまで、家族には何も届かない。**

これは既にほぼ実装されている（pending action / 確認プレビュー）。
だとすれば、**「相談かお願いか」を事前に判定する必要はほとんどない。**

```
ユーザー: 妻にどう言えば角立たない？金曜のお迎え代わってほしくて。

おうちノート:
  今週パパが3日お迎えに行ってるので、
  そこに触れてから頼むと角が立ちにくいと思います。

  例えばこんな感じ:
  「今週ずっとお迎えありがとう。金曜だけ代わってもらえると助かる」

  ─────────────────────
  🙏 金曜のお迎え → ママ （まだ送っていません）
     [この文章で送る]  [直す]  [送らない]
```

- 相談として答える **と同時に** 候補も見せる
- **どちらに判定するかを間違えても事故にならない**（送信は必ず1タップ先）
- ユーザーは「相談モード」「登録モード」を意識しなくていい

現状の `これは私への相談ですか？それとも家族へのお願いですか？` という**逆質問は廃止できる。**
**ユーザーに分類を聞くのをやめて、両方出して選ばせる。**
これは要望文の「これはユーザーに選ばせない方がよい」の、正しい適用先だと思う。

決定論的ガードは残す。ただし役割を変える:
- 現在: 「これは相談だからアクションを作るな」（**判定器**）
- 提案: 「`送らないで` `登録せず` と明示されたら、候補すら出さない」（**明示的な抑制だけ**）

判定の網羅性が要らなくなるので、正規表現の階段を維持し続ける必要がなくなる。

### 6.4 提案: 相談AIに家庭のコンテキストを渡す

`buildAssistantConversationReply` に、少なくとも以下を渡す:

- 直近数ターンの会話
- 今日・明日・今週の予定と担当
- 直近2週間の送迎実績（「今週パパが3日行っている」を言うため）
- 家族の呼び名

これだけで、汎用アシスタントが **おうちノートにしかできない返答**をするようになる。
プライバシー境界（原文を相手に見せない）は変わらない。相談は自分のチャネルの中で閉じている。

**この1点だけで、AI体験の印象が根本的に変わる。**
現状のAIは「どこにでもあるLLM」で、コンテキストを入れた瞬間に「うちのことを知っている相手」になる。

## 7. 日々の利用体験をどう組み立てるか（提案）

### 朝（LINE）— 1通、5行以内

```
おはようございます。

⚠️ 16:30のお迎えとママの会議が重なっています
   [パパが行く] [そのまま] [相談]

🌅 保育園バッグ・水筒・連絡帳
🌙 洗濯・お風呂
```

- 例外がなければ `⚠️` の段は出ない（3行で終わる日があってよい）
- 08:30の「ちゃんとやった？」リマインダーは **既定オフ**

### 日中（LINE）— 思いついた瞬間

```
ユーザー: 明日迎えお願い。あと牛乳買っといて

おうちノート:
  🙏 明日のお迎え → ママ
  🛒 牛乳
  [送る] [直す]
```

1往復。**これは既にできている。** 守るべき。

### 夜（LINE）— 1通、3タップ以内

```
今日おつかれさまでした。

洗濯・お風呂・食器、どうでした？
[ぜんぶやった] [だいたい] [ひとつずつ]
```

- `[ぜんぶやった]` で終わり。追加確認なし
- `[だいたい]` で終わり。翌日 `前回結果未確認` として静かに出る（**今の実装通り。良い**）
- 7択は `[ひとつずつ]` の奥、しかも2択（やった / やらなかった）に減らす

### PWAを開いたとき — 「次に何をすればいいか」が1画面で分かる

```
おうちノート                        ⚙

┌─────────────────────────┐
│ ⚠️ 16:30 お迎え                    │
│    ママの会議と重なっています         │
│    [パパが行く] [そのまま] [相談]     │
└─────────────────────────┘

次は  17:30  保育園お迎え （ママ）

今日やること 4件                      ▾
今週の家族                            ▾

┌─────────────────────────┐
│  何でもどうぞ…              🎙  ▶ │
└─────────────────────────┘

  今日   家族   ＋   買い物   設定
```

**スクロールなしで「今どうすればいいか」が終わる。**
数値タイルなし、セクション18個なし。詳しく見たい人だけが `▾` を開く。

## 9. まとめ（ご依頼の6項目）

### ① このプロダクトを今初めて見た印象

**思想は本物。実装は思想を裏切っている。**

「家庭を仕事のプロジェクト管理にしない」と宣言した設計書が、
14セルのグリッド、7択の結果、6状態のライフサイクル、18セクションのTodayを生んでいる。
悪意や無理解ではなく、**正確さを追求した結果**であり、
5ラウンドの設計レビューが全部「足りているか」を問い、
一度も「多すぎないか」を問わなかった副作用に見える。

### ② 一番良いところ

**「採点しない」という思想が、データモデルまで貫通していること。**

`planned` と `actual` の分離、勝敗・ポイントの仕様禁止、相手の完了を中立に出す、
原文を相手に見せない、`今回は不要` と `できなかった` を潰さない、`大体やった` の逃げ道。

これは夫婦向けプロダクトが失敗する最大の原因（見える化が査定になる）を
思想レベルで回避しており、**後から足せない種類の設計資産**。何があっても守るべき。

### ③ 一番もったいないところ

**LINEで実現できている「分類させない1往復」が、PWAに一切移植されていないこと。**

同じ「牛乳買っといて」が、LINEでは1画面2タップ、PWAでは4画面6タップ。
しかもPWAのAI入口は `✨ おうちコンシェルジュ` という機能名で、10択の1行目。
「AI機能を使う感覚を強くしたくない」という要望と正反対の形になっている。

**PWAがLINEの劣化版の入力フォーム集になっている。**
画面が広く、履歴があり、まとめて操作できるという有利な条件を持ちながら、
一番効く体験だけがLINE専用になっている。

### ④ 最も優先して変えるべきこと

**1つだけ選ぶなら: PWAの `+` から10択を消して、入力欄1つにする。**

これが最短で最大の効果を持つ理由:
- 思想と実装のズレが最も鋭い箇所
- concierge 3画面が1画面に畳める（P2が自動的に付いてくる）
- 「分類しなくていいアプリ」という体験が、初めてPWA側でも成立する
- 9つの入口が消えるので、その先の画面を維持するコストも消える

次点は **Todayの数値タイル削除 + セクション既定折りたたみ**（P3）。
その次が **初期設定ゲートの全解除**（P5）。
この3つで、プロダクトの印象は別物になる。

構造的なリスクとして別枠で **LINE無料枠と定例通知の衝突**（P7）があり、
これはUX改善ではなく前提の破綻なので、
`08:30 / 20:30 / 22:00` の既定オフだけでも早めに入れる価値がある。

### ⑤ 日々の利用体験をどう組み立てるとよいか

**「1日3接点・各接点は5行以内・分類なし」を設計制約にする。**

| 接点 | チャネル | 内容 | 上限 |
|---|---|---|---|
| 朝 | LINE 1通 | 今日の例外 + 自分の担当 | 5行 |
| 日中 | LINE 随時 | 思いついたことを普通に書く | 1往復 |
| 夜 | LINE 1通 | `ぜんぶ / だいたい / ひとつずつ` | 3タップ |
| 随時 | PWA | 次の1件 + 詳しく見たい人だけ `▾` | 1画面 |

**行数・タップ数を「守るべき仕様」として書く。**
現状のドキュメントは「何を出すか」は詳細に定義しているが、
「**どこまでしか出さないか**」を一度も定義していない。
そこが抜けている限り、どの画面も足し算で伸び続ける。

### ⑥ AIをどこにどう置くと自然か

**AIの入口を作らない。入口を全部AIにする。**

- **置き場所は3つだけ:** ①LINEのトーク画面（ほぼ完成）②PWAの `+` ③お願いを作る文脈の中
- **`✨ おうちコンシェルジュ` という名前を捨てる。** 機能名がある限り「AI機能」になる
- **PWAはチャットUIに寄せない。** 入力は会話的に、出力は構造的に。
  チャットはLINEの担当で、PWAは「共有ノート」の担当
- **安全境界を判定から設計へ。**
  「相談かお願いか」を正規表現で当てにいくのをやめ、
  **相談の答えと候補を同時に出して、送信を必ず1タップ先に置く**。
  誤判定が事故にならない構造にすれば、`これは私への相談ですか？` という
  逆質問（＝ユーザーに分類させる行為）を廃止できる
- **相談AIに家庭のコンテキストを渡す。**
  予定・担当・直近の送迎実績・呼び名。これだけで
  「どこにでもあるLLM」が「うちのことを知っている相手」に変わる。
  現状、実データを持っているという唯一の強みを、相談のときだけ使っていない

## 10. 付記: この製品の一番の強みについて

最後に1つ。

「家事ToDo」「スケジュール共有」の領域には既に多くの製品がある。
おうちノートがそれらと違うのは、**「相手に少し言いづらいお願い」を扱おうとしている**点。

これは他のどの家事アプリも扱っていない領域で、
かつ実際の家庭で最も摩耗が起きる部分でもある。

現状の実装では、この価値は

- `+` → 10択 → `お願いを送る` の3階層の奥
- ボトムナビには存在しない
- AIの相談機能は家庭のことを何も知らない一般論

という形で埋もれている。

**この1点を製品の顔に据えるだけで、おうちノートは「もう1つの家事アプリ」ではなくなる。**
上のP1〜P8はすべてそのための地ならしで、
本当に伝えたいのは「一番強い部分が、一番奥に置かれている」ということです。
