# 確定後のLINE会話と送迎担当変更のレビュー

## 問題と原因

登録済みの別件のあと「明日の送りは私に変更してください」が、その別件への訂正として吸収された。会話のgetterは履歴参照のため確定済みも返す契約だが、AI snapshotがstatusを見ず確認待ちとして渡し、fallbackも「に変更」を無条件で前の入力の編集と扱っていた。

別件として解釈された場合も、AIのgeneric requestは実際の送りtaskに紐付かず、受諾後は単なる新規ToDoになる。既存LINEの担当変更は「自分担当のお迎えを相手へお願い」の経路に限られ、相手担当の送りを自分へ変える方向は表せなかった。

## 対応

- getterの履歴参照契約は維持し、status=draftだけを確認待ちとしてAIへ渡す。AI編集の実行側でもdraftを再確認する。
- 閉じた入力への明示参照や短い日付/担当/時刻の訂正は安全に状態を返す。独立した対象付きの用件は新規の経路へ進める。
- 送迎変更の独立した指示をAIより前で読取り専用に解決。世帯・実日付・定義・本番スコープの実taskを使い、曖昧/終了済み/読取失敗時は一般依頼へ落とさない。
- 既存の正規お迎え依頼は維持。それ以外は本人宛て・対象日・task・希望担当を指定したPWAリンクで担当調整を開く。URLは同世帯の大人と未完了の実送迎taskに照合し、合意やmutationとして扱わない。
- 古い誤ったgenericカードの確定も遮断する。保存された日付を保持し、誤送信や別日の変更を防ぐ。
- LINEとPWAの両方の確定入口で同じ送迎意図を検証する。通常の確定済み再送と別人・期限切れの拒否は元の確定RPCに委ねる。
- PWAは自己宛ての依頼と、元担当以外からの未合意依頼を送信しない。明示した話し合い済みの選択後は既存canonical変更へ進む。
- 通常の担当変更依頼も、画面で確認したtask revisionを既存のv2 APIへ渡し、表示後の変更を見落とさない。

## 検証と反映

架空データの実worker HTTPで、閉じた入力後の新規依頼、AI誤create、実例の送り変更、元件の訂正、古い確定再送、古いgenericカード2種類の拒否を検証。PWA実renderで対象日の実task自動表示・希望担当・自己宛て送信拒否・話し合い済み選択後の正規変更・別人/別世帯/期限状態を確認する。LINEの文字数・既存NL回帰・worker認証も維持する。

Deno全体581テスト＋29 HTTP steps、lint、変更した2入口の型チェック、認証matrixが成功。Webは対象53テストと、revision送信を加えた16テスト、型チェック、lint、buildが成功。実Supabase CLIのCIにも、古い誤ったカードの拒否とdraft維持・普通の確定と成功済み再送・別世帯拒否を追加した。

スマホ幅の実Chromeでは既存7ケースに、LINEリンクで未合意の変更を送らないケースと、明示した話し合い済みの確定POSTから再取得してパパ担当になるケースを加え、計9ケースが成功した。APIはCDPのスタブで、実家庭へ副作用を出していない。

DBスキーマは変更せず、既存process-line-inbox、confirm-pending-action、Webを反映する。実家庭の依頼や担当を推測して修正せず、LINE試験送信もしない。必須CI成功後に既存の100関数の範囲でデプロイし、公開コードを照合する。
