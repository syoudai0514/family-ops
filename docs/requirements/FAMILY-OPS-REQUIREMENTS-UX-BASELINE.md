# 2. プロダクトの最上位目的

おうちノートは、単なる家事チェックリストではなく、**家庭運営OS**を目指す。

システムは以下を支援する。

- 今日やるべきことを先回りして整理する。
- 例外・重要事項・期限・担当未解決を埋もれさせない。
- 「誰がやる予定か」と「実際に誰がやったか」を分離して残す。
- お願い、担当調整、共有、引き継ぎ、予定、イベント準備を一つの家庭運営モデルで扱う。
- LINEを日常の主導線にし、PWAは詳細・一括編集・設定・履歴・イベント管理を補完する。
- 実績を残せる一方、夫婦の競争や「やってあげた」感を助長しない。
- AIは入力と整理を楽にするが、重要な担当変更・人間が確定した予定・外部情報を勝手に上書きしない。

# 3. UXの絶対原則

1. **通常ケースを最短にする。** レアケースを扱うために、普段の画面や操作を複雑にしない。
2. **例外は奥に置くが、必要なら必ず記録できる。** 「二人で実施」「コメント付きで難しい」等を毎回見せない。
3. **LINEだけでも今日やることが分かる。** 自分の当日タスクは件数だけに畳まず、LINE本文に表示する。
4. **通知は少なく、情報は欠落させない。** 随時通知が必要なものはその場で知らせ、定時通知を初回通知の置き場にしない。
5. **状態と実績を混ぜない。** 予定担当、現在担当、実施者、登録者、共有者は別概念として扱う。
6. **人の明示確定を自動処理より優先する。** AI・画像解析・Google同期が、人が確定した内容を黙って上書きしない。
7. **曖昧な部分だけ聞く。** AIが理解できた箇所まで再確認させない。
8. **PWA操作で画面を壊さない。** 1件更新ごとの全再読込、スクロール先頭戻りは禁止。
9. **過去の事実を未来ルール変更で書き換えない。** 完了実績・合意履歴・訂正履歴を保持する。
10. **「できなかった」と「入力していない」を混同しない。** 不明を未達として集計しない。

# 4. 家庭コンテキスト

初期の家庭モデルは夫婦2人を前提とする。ただし、初期検証では妻を実LINEユーザーとして追加せず、1つのLINEトークで送信者・受信者の双方を疑似体験できるテストモードを必要とする。

子どもと園情報は以下のように分離する。

- **マサキ:** 年長 / すだちぐみ
- **ウタノ:** 3歳クラス / ゆきぐみ
- **2人は別の保育園。** 園行事、クラスルール、持ち物、画像解析ルールは混在させない。

# 5. コア概念

## 5.1 予定と作業

- **予定:** 家族の時間を押さえるもの。例: 予防接種、七五三、面談、引き取り訓練。
- **ToDo / タスク:** 家庭の作業。例: 水着準備、書類記入、洗濯物を畳む、予約電話。
- **定例:** 曜日や期間ルールから発生するタスク・予定。
- **個別例外:** その日、その期間だけ基本ルールと異なる内容。
- **イベント:** 複数の準備ToDoを束ねるプロジェクト的コンテナ。イベント自体に「取りまとめ担当」は置かない。

## 5.2 担当

担当は少なくとも次を区別する。

- 基本ルール / 基本担当
- 期間・曜日ルール
- 当日・期間のoverride
- 個別合意済み担当
- 現在の予定担当
- 実際の実施者
- 実績を入力した人
- `担当未定`
- `誰でもOK`

**予定担当と実施者は分離する。** 予定がママ、実施がパパでも、過去の予定担当をパパに書き換えない。

## 5.3 情報

- **共有:** 家庭に知らせる情報。原則家庭全体へ共有し、必要時のみ「自分だけ」。
- **引き継ぎ:** 次の担当者や次の時間帯に影響する情報。重要度に応じて確認を求める。
- **状況メモ:** 現在の状態を自然文で表す。通常は最新だけ見せ、履歴を開けば時系列を確認できる。

## 5.4 実績

実績にするのは、**完了した家庭運営上の仕事**である。

含む例:
- 掃除機をかける
- 食器を片付ける
- 洗濯物を畳む
- 買い物へ行く
- 書類を提出する
- 予約をする

原則含めない例:
- 子どもと遊んだ
- 園の先生と少し話した
- 商品をネットで探した
- 七五三の店を調べただけ

「写真館を予約した」は実績、「写真館を調べた」は原則実績ではない。

## 5.5 情報源のAuthority / Conflict原則

同じ予定・担当・期限・準備内容について、人の確定、Google Calendar、園画像等のsource fact、AI inferenceが競合し得るため、**newest-winsを禁止**し、現在の有効値と候補値を分離する。

優先原則:

1. **人が明示的に確定した値・夫婦が合意した値は protected value** とする。外部同期やAIが黙って書き換えない。
2. **Google Calendar等のlinked external source** は、protected valueと競合しない更新のみ自動反映してよい。protected valueと競合する変更は `変更候補 / diff` として提示し、人の確認まで現在値を維持する。
3. **園のお知らせ等に明記されたsource fact** はAI inferenceより強いが、既存のprotected valueをsilent overwriteしない。画像取込は原則candidateとして人が確認してから家庭情報へ確定する。
4. **AI inference / 推測** は常にcandidateであり、人の確定値・source factより弱い。AI推測だけで担当、日付、取消、外部副作用を確定しない。
5. 競合が複数sourceから同時に来ても、1つずつlatest-winsで反映せず、**現在の有効値 + 各候補 + 出典**を比較できること。
6. 競合解消後は、誰が何を採用したか履歴を残す。

この原則をGoogle専用・画像専用に別々に作らず、外部情報/AI入力に共通適用する。

# 6. 担当・ルール・override

## 6.1 期間付き曜日ルール

曜日担当は timeless な固定値ではなく、**有効期間を持つルール**として扱う。

例:
- 9/1-9/30: 木曜送りはママ
- 10/1以降: 木曜送りはパパ

変更時は「この日だけ」「この期間」「今後ずっと」をAIが文脈から推定し、確定前に適用範囲を表示する。

## 6.2 ルール変更時の未来予定

基本ルール変更時は、**基本ルール由来の未来予定だけ再計算**する。

- 個別合意済み
- 明示的override
- 期間限定の例外

は勝手に書き換えない。

さらに、新ルールと既存個別合意が競合する未来予定については、双方に「この個別合意を維持するか」を確認する。

ただし occurrence ごとに通知・承認を増殖させない。同じseries / 同じ合意範囲に属する競合は、原則まとめて:

- `個別合意 6件は維持されます`
- `[すべて維持] [内容を見る]`

のように一括確認する。片方が一部だけ変更を希望した場合、その disputed subset だけを担当調整へ送る。

意見が割れた場合は、元の個別合意を正式担当として維持しつつ `担当調整中` にする。

## 6.3 相手担当を変更する操作

相手担当を変更しようとしたときは、まず **「事前に調整済みか」** を確認する。

- アプリ内に合意履歴がある: そのまま確定可能
- アプリ外で口頭合意済み: `調整済み` と申告すれば確定し、履歴に申告を残す
- 未調整: 元担当を維持し、相手へ担当変更確認を送る

重要な担当変更（送り迎え、通院等）は調整済みでも随時通知する。通知は承認待ちにはせず、

`明日のお迎えはママ担当に変更されました（事前調整済みとして登録） [違う]`

のような**非ブロッキング訂正導線**を持つ。相手が `[違う]` を選んだ場合、事前合意済みという前提が崩れたため、変更前の担当を有効担当へ戻し、`担当調整中` として再調整する。新しい「仮合意」statusは増やさない。

軽微な家事担当変更は朝夜の定時通知下部にまとめてよい。

## 6.4 両方在宅

「二人とも家にいる」は日/状況コンテキストであり、自動的に共同担当にはしない。基本担当は残し、必要なら入れ替えや実施者変更を行う。

## 6.5 担当未定と誰でもOK

- `担当未定`: 本来は担当を決める必要がある。期限が近づけば強く提示する。
- `誰でもOK`: 担当決定そのものが不要。ただし二重対応防止のため、実施前に `[自分がやる]` でその回をclaimする。

claim後は `対応予定: パパ/ママ` とし、できなくなれば本人が `[手放す]` で `誰でもOK` に戻せる。期限到来で自動解除はしない。

claim者が対応不能・連絡不能でも家庭作業を止めないため、もう一方は必要時だけ `[引き継ぐ]` を使える。引き継ぎ操作では「現在○○が対応中」を明示して誤操作を防ぎ、確定するとclaimを新しい人へ移し、元claim者へ状態変更を通知可能にし、履歴を残す。通常画面にtakeover操作を常時強調しない。

`誰でもOK` をclaimして完了しても担当外サポートには数えない。

# 7. お願いと担当調整

## 7.1 種類を分ける

以下を混同しない。

1. **軽いお願い**: 相手に作業をお願いする。
2. **担当変更**: 既存の予定担当を変更する。合意が必要。
3. **共有**: 情報を知らせる。必ずしも作業を発生させない。

## 7.2 受け手の基本UI

お願いへの第一階層は以下だけにする。

- `[やる]`
- `[難しい]`
- `[その他の返答]`

`その他の返答` の中:
- `確認してみる`
- `コメント付きで難しい`
- `相談する`

ユーザー向け文言は「難しい」で統一し、「断る」と混在させない。

## 7.3 確認してみる

`確認してみる` は、**会社予定など自分側を調整して引き受け可能か確認する状態**である。

押した時点で相手へ1回だけ「確認中」を通知する。途中経過は状況メモとして保存できるが、毎回LINE通知しない。最終的に `やる / 難しい` で確定し、その結果だけ再通知する。

`確認中` は了承ではない。返答期限中も元担当/元の責任状態を維持する。

## 7.4 相談する

`相談する` は、相手と別案・条件・折衷案を相談する状態である。

例:
- 18:30なら行ける
- 送りと迎えを交換なら可能
- 金曜なら代われる

自然な会話を続け、AIが合意候補を整理する。**元依頼から条件が変わった合意案は、双方が同じ案を明示確定した時だけ成立**する。片方だけが `[この内容で確定]` している間は `相手確認待ち` であり、元担当/元条件を維持する。

### 7.4.1 依頼・担当調整の最小状態遷移

日常UIに全内部状態を露出させる必要はないが、要求上の真実は以下へ閉じる。

| 現在 | 操作/事象 | 次 | 有効担当/実行責任 |
|---|---|---|---|
| 未回答 | やる | 成立 | 合意した担当へ変更 / 軽いお願いは受け手ToDoへ |
| 未回答 | 難しい | 不成立 | 元状態維持 |
| 未回答 | 確認してみる | 確認中 | 元状態維持 |
| 未回答 | 相談する | 相談中 | 元状態維持 |
| 確認中 | やる | 成立 | 合意内容を反映 |
| 確認中 | 難しい | 不成立 | 元状態維持 |
| 相談中 | 合意案を片方のみ確定 | 相手確認待ち | 元状態維持 |
| 相談中/相手確認待ち | 双方が同じ案を確定 | 成立 | 合意内容を反映 |
| 未回答/確認中/相談中/相手確認待ち | 返答期限超過 | 不成立（期限超過） | 元状態維持 |

期限超過後の古いLINEボタン/操作は、**失効した依頼を復活させない**。遅れて `やる` が来た場合は `この依頼は期限切れです。新しい再提案として送りますか？` とし、新しいnegotiation attemptとして扱う。

以前決めた「期限後も調整継続」は、古いrequest stateを無期限に生かす意味にはしない。期限超過でそのattemptは閉じた上で、underlying task/担当問題を `調整が必要` として残し、ワンタップで再提案を続けられる意味とする。

## 7.5 コメント付きで難しい

`コメント付きで難しい` を選んだ場合のみコメント入力を求める。先に「難しい」を通知してからコメントを別送することは禁止し、**最終結果を1通だけ送る**。

必要ならAIが家族向けに柔らかい表現へ整えるが、送信者が確認できること。

## 7.6 引き受け後 — RequestとToDoの正を一本化

お願いと実行ToDoに独立した「完了の正」を持たせない。

- **了承前:** Request / negotiation が「依頼内容と合意状態」の正。
- **了承成立時:** linked ToDoを作成または既存ToDoへ紐づける。
- **了承後:** linked ToDo が「実行状態・期限・再予定・完了・今回不要等」の正。
- Request側は `誰が何を依頼し、どの内容で合意したか` というprovenance / agreement historyとして保持する。
- 「お願いが完了」はlinked ToDoの状態から派生表示してよいが、request側へ別の独立completion truthを作らない。

了承後にToDoを再予定しても、Requestを別途再予定しない。依頼者が了承済み内容を取消/変更したい場合はagreement changeを成立させ、**成立後にのみlinked ToDoへ一方向に反映**する。

CURRENT実装にrequest側の `completed` 等が存在しても、詳細設計では二重truthを作らないことを優先し、legacy representationをどう収束させるかを決める。

## 7.7 返答期限と作業期限

依頼は内部的に、

- 返答期限
- 実施日時 / 作業期限

を別に持てる。

通常は実施日時だけ入力すれば、返答期限をAI/ルールで提案し、必要時のみ変更する。

## 7.8 返答なし / 期限超過

担当変更の返答期限を超えて成立していない場合、既定では**そのnegotiation attemptを不成立として閉じ、元担当維持**とする。`確認中 / 相談中 / 相手確認待ち` も同じであり、期限超過後の古いpostbackで成立させない。

必要なケースで「期限後も調整継続」を選んでいた場合も、古いattemptを再開するのではなく、underlying task/担当問題を未解決として残し、新しい再提案へつなぐ。

軽いお願いはより弱く扱い、期限超過後は依頼者側に未処理/期限切れとして示す。実行が必須のタスクは、お願いが閉じてもunderlying taskを消さない。

## 7.9 難しいと返された後

軽いお願いは終了してよい。一方、送り迎え等「誰かがやらないと成立しない問題」は、依頼が難しいと返されても問題自体を消さず、担当未解決/担当調整として残す。

## 7.10 依頼内容変更

依頼内容を上書きしない。変更は**変更提案**として履歴を残す。すでに相手が了承済みの場合は、変更部分について再確認する。

## 7.11 依頼取消

- 了承前: 依頼者が自由に取消可能
- 了承後: 相手の確認が必要

# 8. 共有・引き継ぎ

## 8.1 共有範囲と対応担当を分ける

1つの入力から以下を独立して決められる。

- 家庭に共有するか
- ToDoを作るか
- 作るなら誰のToDoか

例: 「明日は水遊び。水着は自分で用意する」は、家庭共有 + 自分のToDoであり、相手へのお願いではない。

AIはタスク化を提案してよいが、勝手に相手へ仕事を割り当てない。

## 8.2 共有の保持期間

共有情報は「いつまで有効か」を持てる。

例:
- 今日だけ
- 明日まで
- 指定日まで
- クリアするまで

情報の有効期限と関連ToDoの完了は別管理する。

## 8.3 引き継ぎの確認

対応が必要・重要な引き継ぎだけ `確認した` を求める。

**確認した = 作業完了ではない。**

引き継ぎを確認しなくても、必要なToDo自体はTodayに存在する。

## 8.4 新規共有の通知

新しく登録された共有・お願い・引き継ぎは、原則として**随時通知**する。朝夜の定時報告を「初めて知らせる場所」にしない。

ただし、同一登録操作から複数の通知対象が生じた場合は1通にまとめ、`返答が必要` を最上部で強調する。

定時LINEでは、まだ意味がある情報・未対応・未確認を整理して再掲する。

## 8.5 相手が自分の仕事を実施した通知

相手が自分担当の家事をやっても、原則として即時に「やってくれた」通知は送らない。状態はリアルタイム更新し、次の朝夜まとめや詳細で `対応済み` と確認できればよい。

恩着せがましい表示を避ける。

## 8.6 情報の更新・訂正

新情報が旧情報を訂正する場合、旧情報を削除せず**無効化/更新履歴**として残す。現在画面には最新状態を表示する。

関連ToDoへの影響はAIが候補化するが、勝手に消さない。

# 9. タスクの時間・期限・状態

## 9.1 任意の日付属性

ToDoは必要に応じて以下を持てる。

- 着手可能日
- やる目安
- 期限
- リマインドオフセット

すべて必須にはしない。タイトルだけでも作成可能。

## 9.2 待ち

正式な `待ち` 状態を持つ。

- 状況メモ
- 次に確認する日（任意）
- 本来の期限

待ち中は通常の未完了nagを抑え、次回確認日でTodayに戻す。ただし本期限が迫る場合は警告する。

## 9.3 途中進捗

普段の家事に「一部完了」ボタンは出さない。必要なタスクだけ、状況メモ・子項目・買い物チェック等で進捗を表現する。

## 9.4 持ち越し

タスクの性質ごとに未完了時の扱いを変える。

- **その回で終了:** ゴミ、薬、送り迎え等
- **終わるまで残す:** 食器、洗濯物等
- **期限まで継続:** 予約、書類、イベント準備
- **次回分と別に残す:** 日ごとに対象が増える作業

LINEでは持ち越しを今日分と混同しない。

## 9.5 今回は不要

`今回は不要` は原則その回だけ。定例ルールには影響しない。同じ定例で不要が続く場合のみ、設定見直し候補を控えめに提案する。

## 9.6 延期/再予定

単なるやり残しと、明示的な再予定を区別する。

- 「今日は無理」だけ: 持ち越しルールに従う
- 「明日の夜やる」: `再予定` として予定日を変更し履歴を残す

## 9.7 前倒し

未来の予定担当は最初から可視化し、他の人が早めに実施できる。

前倒しには2種類を想定する。

- 前倒し推奨: できれば前夜にやると楽
- 事前完了必須: 前日までに終えないと翌日に支障

「前倒しできる」だけを理由に単独リマインドは送らない。既存の夜LINE、Today、PWAの `余力があれば` で軽く提示する。

相手の前倒し実施を翌朝見せるのは、**実際に自分の朝の負担を減らした場合だけ**。

# 10. タスクグループと一括実績

## 10.1 グループの種類

用途によって分ける。

- **日常グループ:** 朝の準備、夜の家事、寝る前等。表示と一括操作のための箱であり、親タスク実績は持たない。
- **プロジェクトコンテナ:** 七五三、入学準備、旅行準備等。進捗や状況を持てるが、親自体を家事実績1件とは数えない。

システムは時間帯・イベント等から自動グループ化でき、必要ならカスタムグループも作成可能。

## 10.2 一括完了

意味のあるまとまりでは `[まとめて完了]` を出せる。

対象:
- 自分担当
- 未完了
- 必須 + 通常

`余力があれば` は一括完了対象外。

押したら即時確定し、その直後に `[例外を修正] [元に戻す]` を出す。毎回確認画面を挟まない。

# 11. 実績入力

## 11.1 基本の3択

夜や翌朝のまとまり入力は以下を基本にする。

- `[全部やった]`
- `[大体やった]`
- `[個別で答える]`

### 全部やった
そのまとまりの自分担当・必須+通常を自分実施として登録する。

### 大体やった
まとまり単位で `概ね対応 / 詳細未確認` の**入力証跡**だけ残す。

`大体やった` は子タスクの第四のstatusではない。子タスクは、すでに個別確定されたものを除き、原則:

- 確認済み完了
- 明示的例外（できなかった / 今回不要 / 中止 / 再予定 等）
- 不明

のいずれかとして扱う。

`大体やった` によって不明な子を一括完了にも一括未達にも変えない。**子タスクの完了件数・未達件数の集計には入れず、そのまとまりの「実績を細かく答えてください」というreconciliation催促だけを閉じる。**

翌日のoperational handlingは各taskの持ち越し性質に従う。

- `その回で終了`: 結果不明のままそのoccurrenceを閉じ、翌日ToDoへは持ち越さない。未達集計もしない。
- `終わるまで残す`: 完了が確認できていないためcarryoverとして残す。ただし `前回結果不明` と区別し、失敗扱いしない。
- `期限まで継続`: 確認済み完了までopenのまま継続する。
- `次回分とは別管理`: 新しいoccurrenceは生成し、前回分はそのtask固有のcarryover ruleに従う。

これにより「入力を閉じること」と「作業を勝手に完了扱いすること」を分離する。

### 個別で答える
`LINEで答える / PWAでまとめて入力` を選べる。

LINEでは、基本は「例外だけ教えて、残りは自分完了」とする。必要なら1件ずつボタン回答するモードに切り替えられる。

## 11.2 実施時刻

家庭実績として厳密な実施時刻は要求しない。

保存するのは基本的に:
- 対象日/対象回
- 実施者
- 結果

監査用として登録日時・修正日時は裏で保持するが、普段は見せない。

翌日に昨日分を入力した場合は、入力日ではなく**元タスクの対象日**へ紐づける。曖昧な場合だけ確認する。

## 11.3 未入力とできなかった

入力がないことを自動で `できなかった` にしない。

- 未入力/不明
- できなかった
- 今回不要
- 中止/不要になった
- 再予定

を区別する。

`大体やった` は子task statusではなく、11.1で定義したgroup-level reconciliation evidenceである。

## 11.4 複数人実施

1つの仕事に複数実施者を持てる。ただしレアケースなので通常UIに常時出さない。

家庭全体の完了件数は1件。個人振り返りでは両者の関与として参照できる。

## 11.5 担当外サポート

予定担当と実施者が異なる場合、システムが自動で担当外サポート候補として判定する。

ただし以下は区別する。

- 事前に担当を正式変更した: 担当外サポートではない
- 相手担当のまま別の人が実施した: 担当外サポート
- 誰でもOKをclaimして実施: 担当外サポートではない

## 11.6 修正

最近の実績は簡単に修正可能。古い実績も修正可能だが、誰がいつ何から何へ修正したか履歴を保持する。

# 12. 買い物

商品ごとに家事実績を1件ずつ数えない。

例:
- 牛乳
- パン
- オムツ

を買った場合、商品チェックは買い忘れ防止のために持つが、実績は **「スーパーで買い物 1件」** とする。

薬局で薬を受け取る等、実際に別の用事なら別実績。

# 13. LINE UX

## 13.1 固定メニュー

基本6入口:

- `今日`
- `入力`
- `追加`
- `お願い`
- `共有`
- `その他`

`追加` は万能入口。`お願い` と `共有` は目的が明確なときのショートカットであり、別のデータモデルにはしない。

## 13.2 追加

`追加` を押したら自由入力を主役にし、下にショートカットを置く。

例:
- 予定
- タスク
- 買い物
- 共有
- お願い

自然文を直接送った場合もAIが分類する。

## 13.3 今日

`今日` は押した時点の最新状態を再計算する。朝・昼・夜で並び順を変える。

優先階層:
1. `🔴 まず確認` - 担当調整、期限リスク、未解決
2. `⚠️ いつもと違うこと`
3. `ℹ️ 引き継ぎ・共有`
4. `✅ もう済んでいること` - 自分の負担を実際に減らす場合のみ
5. `📝 今日やること`

タスクは大きく時間帯で分け、その中で `必須 / 通常 / 余力があれば` とする。

## 13.4 自分と相手の表示

自分の今日タスクはLINE本文に全部表示する。

相手タスクは通常は件数要約。ただし以下は具体表示する。
- 送り迎え
- 重要な予定
- 今日だけの変更
- 自分の行動に影響する相手担当

必要なら `[相手の分も見る]` で展開する。

## 13.5 入力

`入力` はその時点で最も自然な入力対象を自動で開く。

例: 夜なら夜の家事。

他に:
- 朝の未入力
- 昨日分修正
- 予定外実績追加

へ切り替えられる。

## 13.6 その他

日常操作ではなく、たまに使う管理系をまとめる。

例:
- 家族の予定
- イベント・準備
- 買い物リスト
- 基本担当・曜日ルール
- 履歴・実績
- 設定
- PWAを開く

# 14. 定時LINEと通知

## 14.1 基本時刻

- **平日朝:** 6:30
- **土日祝朝:** 9:00
- **夜:** 20:30

家庭設定で変更でき、その日だけの例外も許容する。

## 14.2 通知方針

基本scheduled pushは朝と夜のみ。

ただし以下は必要に応じて随時通知する。
- 新しいお願い
- 担当変更/確認
- 新しい重要共有/引き継ぎ
- 予定変更
- 期限リスク
- その他、今知ることで行動が変わるもの

随時か定時まとめかは、種類・日時・影響度から自動判定し、必要時のみ変更可能。

## 14.3 朝LINE

自分の朝・夜タスクをすべて確認できる。重要事項を先頭に置き、通常タスクは時間順で並べる。

## 14.4 夜LINE

夜は「今日の全履歴」を再掲しない。

朝の通常タスクが完了済みなら `朝 4/4 完了` 程度にまとめる。

具体表示するのは:
- 未完了
- 未入力
- 変更
- 今夜やること
- 明日に影響する準備
- 軽微な担当変更のまとめ
- 実績入力

# 15. PWA UX

PWAはLINEの別世界ではなく、同じ作業を詳しく操作するビューである。

LINEからPWAへ移動するときは、PWAトップではなく、対象日・対象グループ・対象依頼・対象イベント等へ**deep link**する。

LINEで既に入力した状態も引き継ぐ。

PWAで保存後はPWA内で成功表示し、自分宛てLINEへ「保存しました」と返さない。

相手へのお願い・共有等、本当に相手へ通知が必要な操作だけ通常どおり通知する。

実績一覧では、1件変更ごとの全再読み込み・スクロール先頭戻りを禁止する。

# 16. AI入力・自然文処理

## 16.1 複数意図

1つのLINEに複数内容を書ける。

例:
「明日は水遊び。水着準備しとく。牛乳なくなりそう。金曜のお迎えお願い。今日は掃除機かけた。」

AIは:
- 共有
- 自分ToDo
- 買い物
- お願い
- 実績

へ分解し、1画面で確認してまとめて登録する。

## 16.2 曖昧箇所だけ確認

一部だけ意味が曖昧な場合、理解済み部分を再質問しない。曖昧箇所だけ選択・入力を求める。

## 16.3 家庭内用語

家庭独自の略称・言い回しを学習可能にする。

例:
- 送り
- 迎え
- 着替え
- 夜の家事

ただし、学習するのはまず**言葉の意味**であり、担当ルールそのものをAIが勝手に変えない。

家庭用語は設定で確認・修正・削除可能にする。

## 16.4 重要度

重要度はタスク種類、期限、今日への影響等から自動判定し、必要時だけユーザーが変更する。

重要度を通知回数へ直結させない。主に表示順位・期限リスク強調へ使う。

## 16.5 所要時間

任意で標準所要時間を持てる。定例・よく使う作業は標準値を設定可能。

実際に何分かかったかを毎回入力させず、労働時間ランキングのためではなく、空き時間でできる作業提案等に使う。

## 16.6 重複検出

同じタスク・予定・共有らしいものを検出しても勝手に統合しない。

- 既存を使う
- 更新する
- 別件として追加

を必要なときだけ確認する。

# 17. イベント・準備

イベント作成時は、イベント種別のテンプレート + 実際の内容を使ったAI追加提案を行う。

AIが大量のToDoを勝手に確定せず、ユーザーがレビューして登録する。

イベントに全体取りまとめ役は置かない。各準備ToDoに担当を持つ。

イベントレベルのLINE通知は毎週定例で送らず、以下の意味ある節目/リスク時のみ:
- イベント接近
- 今週期限の準備
- 担当未定
- 期限超過
- イベント日変更

複雑なタスク依存DAGは本Baselineでは必須化しない。実用上の順序は `待ち`, 状況メモ, 次回確認日等で表現し、独立レビューで不足を評価する。

# 18. Google Calendarとの境界

## 18.1 基本原則

- **Google Calendar:** 家族の時間を押さえる予定
- **おうちノート:** 家庭の作業・準備・お願い・実績

ToDoは基本おうちノートのみ。必要なToDoだけ個別に `カレンダーにも表示` 可能。

LINEのTodayでは両者を統合表示する。

## 18.2 Google側で日時変更

Google予定の日時変更は、**5.5のAuthority原則に従って**扱う。

- おうちノート側にprotected human-confirmed valueとの競合がない: linked Google変更を自動反映してよい。
- 夫婦合意、予約済み時刻、手動確定等のprotected valueと競合する: 現在値を維持し、Google変更をcandidate/diffとして提示する。

関連準備に影響があれば、AIが変更候補を提示する。予約済み等を勝手に動かさない。

## 18.3 Google側で削除

即削除しない。

選択肢:
- 予定を中止
- 別日に変更予定
- Googleだけから消した

中止時は未完了準備を不要候補にし、完了実績は残す。

別日に変更予定なら `待ち` にして新日程確定後に再配置可能。

## 18.4 重複

Google側に同一と思われる予定があれば、自動で二重作成せず、既存Google予定へ紐づけるか確認する。

## 18.5 競合

Google固有のlatest-wins ruleは持たず、5.5の共通Authority原則を適用する。

人が手動確定した内容、夫婦合意済み内容、AI/画像解析、Google同期の情報が競合した場合は、黙って上書きせず差分を提示する。競合解消まではprotected current valueを有効値として維持する。

# 19. 園のお知らせ・コドモン画像連携

## 19.1 目的

保育園の掲示物写真、コドモン等のスクリーンショットから、必要な家庭情報を**予定・共有・準備ToDoまで変換**する。

単なるOCRを目的としない。

## 19.2 画像送信時

LINEに画像を送ったら軽く内容判定する。

- 園のお知らせ / コドモン / 予定表らしい: 解析候補を出す
- 普通の家族写真: 家庭運営情報の解析提案を出さない

`追加 → 画像から取り込む` から入った場合は解析前提。

## 19.3 子ども・園判定

園名、ロゴ、クラス名、画面形式等から自動判定する。

- マサキ: すだちぐみ
- ウタノ: ゆきぐみ
- 別園

曖昧な場合だけ `マサキ / ウタノ` 等を確認する。

## 19.4 関係ある情報だけ抽出

予定表に他クラス・他児童の情報が写っていても、家庭に関係する項目だけ構造化・登録候補化する。

AIが対象か迷う項目だけ確認する。

## 19.5 明記情報とAI推測を分離

画面上でもデータ上でも明確に分ける。

例:
- `お知らせに記載`: 9/20 食育
- `AIの準備提案`: 前日にエプロン準備

「園が言ったこと」と「AIが先読みしたこと」を混同させない。

## 19.6 園ごとの確認済みルール

ユーザーが確認・登録した関係を、園・子ども単位で確認済みルールとして蓄積可能。

例:
- 食育 → エプロン
- 絵の具 → 汚れてよい服
- プール → 水着セット

AIが一度推測しただけでは確認済みルールへ昇格しない。

## 19.7 複数画像

短時間に連続した複数画像は、同じ資料かAIが判定してまとめて解析可能。

同園・同クラス・同じ通知の連続ページなら統合候補。別園等なら自動で分ける。

## 19.8 解析確認

予定、対象、日付、持ち物、タスク等を1画面で確認し、項目単位で修正できる。

登録前に全項目を一から入力し直させない。

## 19.9 元画像 / Privacy invariant

登録情報に元画像/スクショを出典として紐づける。

夫婦双方が詳細から参照可能だが、普段のLINEへ画像を再送しない。

raw画像について、保持日数・storage方式は詳細設計へ送るが、以下はBaseline-level invariantとする。

- raw画像は**家庭内private data**として扱う。
- 他児童名・他クラス等、家庭の構造化情報に不要な第三者情報は抽出・学習・二次利用しない。
- raw画像はユーザーがいつでも削除できる。
- raw画像削除後も、ユーザーが確認済みの家庭情報・予定・ToDo・変更履歴だけは維持できる。
- raw画像を削除した後に抽出内容を訂正する場合も、元画像がないことを明示し、既存の確定履歴をsilent rewriteしない。

一定期間後に元画像だけ整理・削除できる。構造化した予定・タスク・履歴は残る。

## 19.10 新しいお知らせによる変更

新しい画像が既存予定を変更・延期・中止している場合、関連する既存予定・準備ToDoまで含めた変更候補を出す。

例:
- 食育 9/18 → 9/25
- エプロン準備 9/17夜 → 9/24夜

旧情報・旧画像・変更履歴は残す。

## 19.11 情報競合

5.5の共通Authority原則を適用する。

手入力確定と画像情報が食い違う場合、最後に読み込んだものを自動採用しない。現在確定値と新しいsource fact / AI inferenceを出典付きで並べ、ユーザーに決めてもらう。

## 19.12 月間予定表

大量の予定がある場合、家庭に影響するものを `登録おすすめ` として優先し、残りは `その他の予定` から確認できる。

AIが勝手に捨てない。

優先例:
- 持ち物あり
- 服装指定あり
- 保護者対応あり
- 時間変更あり
- 提出物あり

## 19.13 定例・期間ルール

「7-8月 毎週火木プール」等を、期間付き定例候補として認識する。

AIが自動で恒久ルール化せず、適用期間と発生予定を確認後に登録する。

## 19.14 その日だけの例外

定例に対する「この日だけ中止/変更」は定例本体を壊さず、その回だけ例外化する。

関連準備もその回だけ不要/移動候補にする。

## 19.15 提出物

「9/15までに健康調査票提出」等は基本 **期限付きToDo** とする。

必要なら準備ToDo候補も出す。Google Calendarには自動投入しない。

## 19.16 URL・QR・提出方法

お知らせ内のURL/QR/回答先を高確度で読める場合、ToDoに `実行先` として紐づける。

例:
- `[回答フォームを開く]`
- `[元のお知らせを見る]`

確度が低い場合は勝手にリンク確定しない。

## 19.17 完了証跡

提出・申込み系も普段は1タップ完了。

必要な場合だけ、完了メモ・完了画面スクショ等を任意添付できる。

日常家事には証跡UIを常時出さない。

# 20. 1人LINEテストモード

妻を本番LINEユーザーとして追加する前に、1つのLINEトークで双方の流れをテストできること。

例:
- パパがお願い送信
- 同一トークに `🧪 テスト: ママへの通知`
- 仮想ママとして `やる / 難しい` 等を操作
- 同一トークに `🧪 テスト: パパへの返答`

要件:
- 実際の操作ユーザーと疑似 actor を分離して保存する。
- 本番2人運用と同じ**domain validation / state-transition logic**を再利用する。
- 一方で、同じ外部副作用は起こさない。通常の1人テストモードでは、simulated actor起因で実ユーザーへのLINE通知、Google Calendar write、production notification outbox等の外部副作用を発生させない。
- すべてのテストデータ/イベント/合意はtest由来と常時識別可能にし、本番分析から**既定で除外**する。「除外可能」だけにしない。
- simulated actorの確認・了承・口頭合意申告を、後から追加した実ママ本人の合意へ昇格させない。
- 実ママ追加時、未解決のsimulated request / assignment negotiation / confirmationは本番へ自動移行しない。必要なものだけ実ユーザーに対して再確認/再提案する。
- test終了後も同じcore domain modelを使い、実ユーザー追加だけで2人運用へ移れるようにするが、test evidenceとproduction evidenceは明確に分離する。
- テスト専用の別family domain modelは作らない。外部adapter / delivery boundaryでsandbox/no-opできること。

# 21. 履歴・振り返り

振り返りはLINEで定期pushしない。

PWAの履歴/振り返りの奥に置き、必要ならLINE自然文から呼び出せる。

例:
- 今月どれくらいやった？
- 担当外でやったこと教えて

最初は個人の:
- 完了
- 担当外サポート
- 予定外の家庭作業
- よくやるカテゴリ

を見せ、必要なら家庭全体表示へ。

競争ランキングや「どちらが勝った」という見せ方は避ける。件数は参考値として扱う。

# 22. 削除・不要・中止

- **削除:** 登録ミス等、そもそも存在すべきでなかったもの
- **今回は不要:** この回だけ不要
- **中止:** 実在した予定/作業が中止になった
- **不要になった:** 外部事情等で実施する必要が消えた

すでに実績が付いたものを削除して過去の事実まで消さない。必要なら訂正履歴で処理する。

# 23. 非機能・安全設計上の要求

本Baselineでは具体技術を固定しないが、詳細設計で最低限検証すべき事項:

- LINE rich menu / Flex / conversation stateの実現可能性
- 画像・スクリーンショットの保存期間、容量、削除、アクセス制御
- 保育園画像に他児童情報が写る場合のプライバシー
- QR/URL抽出の安全性
- Google Calendar同期のidempotency、duplicate、conflict
- recurring rule / override / individual agreementの整合性
- 監査履歴と個人実績集計の分離
- テストモードデータの隔離と外部副作用遮断
- 通知/webhookの重複防止と再送耐性
- PWA deep link / auth / state restoration
- LINE/PWAでの同時更新時の競合
- AI誤解釈時に人が短時間で修正できること

ユーザーから見た期待結果として、詳細設計方式にかかわらず以下を満たす。

1. **同じ操作の重複配送/再送は二度成立しない。** 遅延した古いLINEボタンやduplicate webhookで、完了・了承・担当変更を再実行/復活させない。処理済みなら `すでに対応済み`、失効済みなら `期限切れ/最新状態を確認` と返せること。
2. **LINEとPWAの同時操作でsilent overwriteしない。** 同一taskへ同じ完了操作が重なればidempotentに扱い、異なるactor/異なる状態変更が競合する場合は最新状態を示して再確認する。
3. すでに別actorが完了したtaskへ別actorが完了を送った場合、実施者を黙って置換せず、`すでに○○が完了しています / 共同実施として追加するか` 等の明示的解決を行う。
4. staleなrequest/negotiation actionは、最新状態を逆戻りさせない。
