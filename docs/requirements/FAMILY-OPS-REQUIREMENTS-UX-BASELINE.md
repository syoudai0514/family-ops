# 1. 文書の目的とSource of Truth

本書は、家族向け家庭運営アプリ「おうちノート / Family Ops」の次期要求・UX方針を、実装前のレビュー可能なベースラインとして固定するものである。

本フェーズでは、DB schema、migration、LINE Messaging API、Google Calendar同期方式等の詳細実装は確定しない。まず「家庭で毎日使ったときに本当に回るか」を基準に、業務ルール、状態遷移、LINE/PWAの責務、AI介入範囲、通知、履歴・実績の意味を定義する。

`main` にmergeされた時点から本書を **要求・UXに関する唯一の正（Source of Truth）** とする。

運用ルール:

1. 新しい要求判断は会話・Issue・PRコメントだけで確定させず、本書へ反映して初めて確定扱いにする。
2. 要求に影響する実装PRは、同じPRまたは先行docs PRで本書も更新する。
3. 本書と過去会話・旧PR・旧設計書が矛盾する場合、要求・UXについては本書を優先する。後続ADRが明示的に置換を宣言する場合だけ例外とする。
4. `V2`, `FINAL`, `LATEST` 等の平行コピーを増殖させず、同じcanonical pathを更新し続ける。履歴はGit historyで管理する。
5. 独立レビューで採用した指摘は本書へ統合して初めて確定とする。
6. DOCX/PDFは配布用exportであり、canonical Markdownを生成元とする。

# 2. プロダクトの最上位目的

おうちノートは単なる家事チェックリストではなく、**家庭運営OS**を目指す。

- 今日やるべきことを先回りして整理する。
- 例外、重要事項、期限、担当未解決を埋もれさせない。
- 「誰がやる予定か」と「実際に誰がやったか」を分離して残す。
- お願い、担当調整、共有、引き継ぎ、予定、イベント準備、買い物、実績を一つの家庭運営モデルで扱う。
- LINEを日常の主導線にし、PWAを詳細・一括編集・設定・履歴・イベント管理の補完にする。
- 実績を残せる一方、夫婦の競争や「やってあげた」感を助長しない。
- AIは入力と整理を楽にするが、重要な担当変更、人が確定した予定、外部情報を勝手に上書きしない。

# 3. UXの絶対原則

1. **通常ケースを最短にする。** レアケースのために普段の画面や操作を複雑にしない。
2. **例外は奥に置くが、必要なら記録できる。** 複数人実施、コメント付き返答等を毎回見せない。
3. **LINEだけでも今日やることが分かる。** 自分の当日タスクは件数だけに畳まず本文に出す。
4. **通知は少なく、初回通知を遅らせない。** 新しい依頼・共有等を朝夜まとめまで寝かせない。朝夜は再整理の場。
5. **状態と実績を混ぜない。** 予定担当、現在担当、実施者、入力者、共有者を区別する。
6. **人の明示確定を自動処理より優先する。** AI、画像解析、Google同期は黙って上書きしない。
7. **曖昧な部分だけ聞く。** AIが理解した箇所まで再質問しない。
8. **PWAで連続入力を壊さない。** 1件更新ごとの全reload、スクロール先頭戻りは禁止。
9. **過去の事実を未来ルール変更で書き換えない。** 完了実績・合意履歴・訂正履歴を保持する。
10. **未入力と未達を混同しない。** 入力忘れを「できなかった」にしない。

# 4. 家庭コンテキスト

初期の業務モデルは夫婦2人を前提とする。ただし初期検証では妻を実LINEユーザーとして追加せず、1つのLINEトークでパパ/ママ双方を疑似操作できるテストモードを必要とする。

子どもと園情報:

- **マサキ:** 年長 / すだちぐみ
- **ウタノ:** 3歳クラス / ゆきぐみ
- **2人は別の保育園。** 園行事、クラスルール、持ち物、画像解析ルールは園・子ども単位で分離する。

# 5. コア概念

## 5.1 予定・ToDo・定例・イベント

- **予定:** 家族の時間を押さえるもの。例: 予防接種、七五三、面談、引き取り訓練。
- **ToDo:** 家庭の作業。例: 水着準備、書類記入、洗濯物、予約電話。
- **定例:** 曜日や期間ルールから発生する予定/ToDo。
- **個別例外:** その日・期間だけ基本ルールと異なる内容。
- **イベント:** 複数準備ToDoを束ねるproject container。イベント全体の「取りまとめ担当」は置かない。

## 5.2 担当の概念

少なくとも以下を区別する。

- 基本ルール / 基本担当
- 期間・曜日ルール
- 当日・期間override
- 個別合意済み担当
- 現在の予定担当
- 実際の実施者
- 実績を入力した人
- `担当未定`
- `誰でもOK`

**予定担当と実施者は別。** 予定ママ・実施パパでも、過去の予定担当をパパへ書き換えない。

## 5.3 共有・引き継ぎ・状況

- **共有:** 家庭に知らせる情報。原則家庭全体、必要時のみ「自分だけ」。
- **引き継ぎ:** 次の担当者/時間帯に影響する情報。対応必要なものだけ確認要求を持てる。
- **状況メモ:** `進行中 / 候補2店、人数確認待ち` 等。通常は最新だけ表示し、履歴を開けば時系列を確認できる。

## 5.4 実績

実績は **完了した家庭運営上の仕事** を対象とする。

含む例: 掃除機、食器片付け、洗濯物を畳む、買い物、提出、予約。
原則含めない例: 子どもと遊ぶ、少し話す、ネットで探す、調べただけ。

「予約した」は実績。「調べた」は原則実績にしない。

# 6. 担当ルール・override・合意

## 6.1 期間付き曜日ルール

曜日担当はtimeless固定値ではなく、有効期間を持つ。

例:
- 9/1-9/30 木曜送り: ママ
- 10/1以降 木曜送り: パパ

「この日だけ / この期間 / 今後ずっと」はAIが文脈から推定し、確定前に適用範囲を見せる。

## 6.2 基本ルール変更時

基本ルール由来の未来予定だけ再計算する。個別合意、明示override、期間限定例外は勝手に書き換えない。

新ルールと既存個別合意が競合する未来予定は、双方へ「個別合意を維持するか」を確認する。

意見が割れた場合は、**元の個別合意を正式担当として維持したまま `担当調整中`** にする。

## 6.3 相手担当の変更

担当を変更しようとした時は、まず `調整済み / まだ調整していない` を確認する。

- アプリ内に合意履歴あり: 再確認せず確定可能。
- 口頭等で調整済み: `調整済み` と申告すれば確定し、監査履歴に残す。
- 未調整: 元担当を維持し、相手へ確認依頼を送る。

送り迎え・通院等の重要な調整済み変更は随時通知。軽微な家事担当変更は朝夜定時通知の下部で共有してよい。

## 6.4 両方在宅

「二人とも在宅」はcontextであり、自動的に共同担当にはしない。基本担当を残し、必要なら入れ替える。

## 6.5 担当未定 / 誰でもOK

- `担当未定`: 本来は担当を決める必要がある。期限接近で強く提示する。
- `誰でもOK`: 担当を決める必要はない。ただし二重対応防止のため、実施前に `[自分がやる]` でその回をclaimする。

claim後は `対応予定: パパ/ママ`。できなくなれば本人が `[手放す]` で `誰でもOK` に戻せる。期限で勝手に自動解除しない。

`誰でもOK` をclaimして完了しても担当外サポートには数えない。

# 7. お願い・担当調整

## 7.1 種類を分ける

1. **軽いお願い** — 相手に作業を頼む。
2. **担当変更** — 既存予定担当を変える。合意が必要。
3. **共有** — 情報を知らせる。必ずしも作業を発生させない。

## 7.2 受け手の第一階層

お願いへの基本ボタンは以下だけ。

- `[やる]`
- `[難しい]`
- `[その他の返答]`

`その他の返答`:
- `確認してみる`
- `コメント付きで難しい`
- `相談する`

ユーザー向け表現は「難しい」で統一し、「断る」と混在させない。

## 7.3 確認してみる / 相談する

`確認してみる` = 会社予定等、自分側を調整して引き受け可能か確認する。

押した時点で相手へ1回だけ「確認中」を通知。途中経過は状況メモとして保存できるが通知を連発しない。最終的に `やる / 難しい` で確定し、その結果だけ再通知する。

`相談する` = 相手と条件・代替案・折衷案を相談する。
例: 18:30なら可能、送りと迎え交換なら可能、金曜なら代われる。
自然会話からAIが合意候補を整理し、人が正式確定する。

## 7.4 コメント付きで難しい

`コメント付きで難しい` を選んだ時だけコメント入力。先に「難しい」を通知し、後からコメントを別送する2通構成は禁止。最終結果を1通だけ送る。

必要ならAIが柔らかい家庭向け表現へ整えるが、送信者が確認できること。

## 7.5 引き受け後

`やる` を押したお願いは受け手の通常ToDoへ合流する。裏では依頼元、依頼日時、引受日時、完了者等を保持する。

## 7.6 返答期限 / 実施期限

依頼は内部的に `返答期限` と `実施日時/期限` を別に持てる。通常は実施日時だけ入れれば返答期限をAI/ルールで提案し、必要時だけ変更する。

## 7.7 返答期限超過

担当変更は期限まで元担当を維持。期限超過時は原則 **調整不成立 + 元担当維持**。必要なケースだけ「期限後も調整継続」を指定できる。

軽いお願いは強くnagせず、期限がある場合にTodayへ出し、期限超過は依頼者側に未対応として見せる。

## 7.8 難しい後 / 変更 / 取消

- 軽いお願いが `難しい`: 原則終了。
- 送り迎え等、誰かが対応しないと成立しない問題: `難しい` でも問題自体は `担当未解決/担当調整` として残す。
- 依頼内容変更: 上書きではなく **変更提案** として履歴を残し、了承済み内容を勝手に変えない。
- 了承前の取消: 依頼者が自由に取消可能。
- 了承後の取消: 相手確認が必要。

# 8. 共有・引き継ぎ・情報寿命

## 8.1 共有範囲と担当は別軸

「誰に知らせるか」と「誰が対応するか」を分離する。

例: `明日は水遊び。水着は自分で準備する` は、家庭全体へ共有 + 自分ToDo。相手へのお願いではない。

AIは ①共有するか ②ToDoを作るか ③担当は誰か を整理するが、相手への割当を勝手に確定しない。

## 8.2 共有の既定

共有として登録した情報は家庭全体がdefault。必要なものだけ `自分だけ` にできる。

## 8.3 引き継ぎ確認

軽い情報共有は送信で完了。対応が必要な引き継ぎだけ `確認した` を求める。

`確認した` と `作業完了` は別。

## 8.4 有効期間

共有/引き継ぎは `今日まで / 明日まで / 日付指定 / 解除まで` 等の有効期間を持てる。関連ToDoが完了しても、情報がまだ有効ならTodayに残す。

期限後はActive Todayから外れるが履歴には残す。

## 8.5 訂正・変更

新情報で旧情報を無効化/更新し、現在画面には最新状態を出す。履歴は残す。
関連ToDoへの影響をAIが検出して変更候補を出すが、勝手に消さない。完了実績は消さない。

# 9. タスクの時間・持ち越し・状態

## 9.1 日付関連属性

必要に応じて以下を任意で持つ。

- 着手可能
- やる目安
- 期限
- reminder offset

すべて必須にはしない。タイトルだけの簡単登録を可能にする。

## 9.2 待ち

正式な `待ち` 状態 + 任意の `次に確認する日` を持てる。
待ち中は通常の未完了nagを抑えるが、hard deadline接近時は警告する。

## 9.3 未完了時の扱い

タスク性質ごとに持ち越しルールを持つ。

- その回で終了: ゴミ、薬、送り迎え等
- 終わるまで残す: 食器、洗濯物、予約等
- 期限まで継続: 書類、イベント準備等
- 次回分と別に残す: 日ごとの洗濯物等

LINEでは持ち越しを今日分と混ぜず別枠にする。

## 9.4 今回不要 / 再予定

`今回は不要` は原則その回だけ。定例ルールは変更しない。同じ定例で不要が続く時だけ控えめに見直し提案。

単なるやり残しと、明示的な `明日の夜にやる` 等の再予定を区別する。明示的に予定を変えた時だけ `再予定` として扱い、未達と同一集計にしない。

## 9.5 進捗

日常タスクに常時 `一部完了` ボタンは出さない。必要なタスクだけ状況メモ、subitems、買い物チェック等で進捗を表現する。

## 9.6 重要度 / 所要時間

重要度は種類、期限、今日への影響から基本自動判定し、必要時だけ変更。重要度と通知回数は直結させず、表示順位やrisk強調に使う。

標準所要時間は任意。毎回実時間を聞かず、空き時間提案等の補助情報に使う。

# 10. 実績・一括入力・履歴

## 10.1 通常入力

通常日の実績入力は以下を中心にする。

- `全部やった`
- `大体やった`
- `個別で答える`

`全部やった` は、そのまとまりの **自分担当 + 必須/通常 + 未完了** を自分実施として一括登録する。相手担当、完了済み、`余力があれば` は巻き込まない。

`大体やった` は、まとまり単位で `概ね対応 / 詳細未確認` と記録し、子タスクの完了件数・未達件数のどちらにも入れない。翌日以降の入力催促はそこで閉じる。

`個別で答える` は `LINEで答える / PWAでまとめて入力` を選べる。

## 10.2 LINE個別入力

基本は **例外だけ答える**。

例: `お風呂はママ、掃除機はできなかった` と入力し、残りは自分完了として候補化する。
必要なら `1件ずつ答える` modeへ切替可能。

## 10.3 グループと一括完了

日常の `朝の準備 / 夜の家事 / 寝る前` は表示・一括操作の箱。親自体を実績1件にしない。

イベント等はproject containerとして進捗を持てるが、親を実績件数にしない。

意味あるまとまりでは `[まとめて自分が完了]` を使える。検索結果や「今週全部」のような広すぎる集合には一括完了を出さない。

一括完了は即確定し、直後に `[例外を修正] [元に戻す]` を出す。毎回確認画面を挟まない。

## 10.4 複数人実施

1タスクに複数実施者を持てる。ただしレアケースなので通常UIを複雑にしない。通常はcheck = 自分実施。必要時だけ実施者変更から `自分 / 相手 / 二人` を選ぶ。

家庭全体の完了タスク数は1件。個人履歴には双方の関与を出せる。

## 10.5 担当外サポート

予定担当と実施者が違う場合、担当外サポートを自動推定する。

ただし、事前に担当変更が合意済みの場合は単なる担当変更であり、旧担当の失敗や担当外サポートとして扱わない。

未来の相手担当を早めにやる `先回りサポート` も区別できる。

LINEでは「やってあげた」を都度強調しない。自分の負担が実際に減る場合だけ、次の朝等に `準備済み` と状態として見せる。

## 10.6 実績時刻 / 対象日

ユーザー向けの実績時刻管理は原則不要。登録時刻・登録者・修正時刻は監査用に裏で保持する。

翌日に前日分を入力しても、元タスクの対象日に紐づける。曖昧な時だけ確認する。

## 10.7 未入力

入力なしを自動で `できなかった` にしない。
翌朝等に `全部やった / 大体やった / 個別で答える` で補完できる。
古い未入力は分析上 `不明` とし、未達件数に含めない。

## 10.8 訂正

最近の実績は容易に修正できる。古い実績も修正可能だが、誰がいつ何から何へ変えたか訂正履歴を残す。通常画面は最新状態だけ表示する。

# 11. 買い物

商品数を家事実績件数にしない。

例: スーパーで牛乳・パン・オムツを購入 = **買い物という行動1件の実績**。
薬局で薬を受け取る等、別の用事なら別実績。

商品ごとのcheckboxは買い忘れ防止のために使い、家事実績数とは分離する。

# 12. LINE UX

## 12.1 固定入口

基本の6入口:

- `今日`
- `入力`
- `追加`
- `お願い`
- `共有`
- `その他`

`追加` は万能入口。`お願い` と `共有` は目的が明確な時のshortcutであり、別の業務ロジックにはしない。

## 12.2 追加

自由入力を主役にし、下に `予定 / 買い物 / タスク / その他` 等のshortcutを置く。

自然文を直接送った場合もAIが分類する。

1メッセージに複数意図があれば、共有・自分ToDo・買い物・お願い・実績等に分解し、1画面でまとめて確認して登録する。

AIが一部だけ曖昧なら、その箇所だけ質問する。

家庭内の略称・用語を学習可能にするが、言葉の意味を覚えることと、担当ルールを自動変更することは分離する。

## 12.3 今日

`今日` は押した時点の最新状態で再計算し、時間帯によって並び順も変える。

朝: 朝のやること、今日の予定、夜のやること。
昼: まだ必要な対応、これからの予定、夜。
夜: 未完了、夜、明日に影響する準備、実績入力。

完了済みを消して履歴不明にせず、必要なら下位表示で確認可能。

## 12.4 入力

`入力` は「何を入力しますか？」から始めず、その時点で最も自然な入力対象を最初に出す。

例: 夜なら夜の家事。別の入力対象、予定外実績、昨日分修正へ切替可能。

## 12.5 その他

日常操作以外の管理・一覧・設定をまとめる。

例: 家族の予定、イベント、買い物リスト、基本担当・曜日ルール、履歴・実績、設定、PWA。

# 13. LINE通知

## 13.1 定時

scheduled pushの中心は以下。

- **平日朝 6:30**
- **土日祝朝 9:00**
- **夜 20:30**

必要なら家庭設定・当日例外で変更できる。

新しい依頼・共有等を定時まで待たせない。定時通知は **未対応・現在必要な内容を整理して再掲する場**。

## 13.2 朝LINEの階層

基本順序:

1. `🔴 まず確認` — 担当調整、期限risk
2. `⚠️ いつもと違うこと` — special plan
3. `ℹ️ 引き継ぎ・共有`
4. `✅ もう済んでいること` — 自分の負担が減る情報だけ
5. `📝 今日やること`

タスクは時間帯で大分類し、その中で `必須 / 通常 / 余力があれば`。

**自分の当日タスクはLINEに全部書く。** 相手の通常タスクは要約し、迎え担当・重要変更・自分に影響するものだけ具体表示する。

## 13.3 夜LINE

朝に完了した通常タスクを全部再掲しない。`朝 4/4 完了` 程度でよい。未入力、未完了、変更がある朝タスクだけ具体表示する。

20:30は、夜の残件、明日に影響する準備、実績入力を中心にする。

## 13.4 随時通知

依頼、担当変更、引き継ぎ、共有は原則登録時に随時通知し、定時が初回通知にならないようにする。

ただし軽微な調整済み家事担当変更等は定時下部へまとめてよい。

通知タイミングは種類・日時・影響度から自動判定し、必要時だけ変更可能。

同じ登録操作から複数通知対象が生じた場合は1通にまとめ、**返答が必要なものを最上部**に置く。別タイミングの事項を一定時間溜めて遅延配信はしない。

## 13.5 相手が実施した時

相手が自分予定のタスクを完了しても、都度 `相手がやってくれました` 通知は送らない。状態はリアルタイムで `対応済み` にし、次のまとめで必要な範囲だけ見せる。

# 14. LINE ↔ PWA

LINEからPWAへ行く時はトップではなく、**今やろうとしていた対象へdeep link**する。

例: `9/2 夜の家事・実績入力` を直接開き、LINEで入力済みの状態も反映する。

PWA保存後はPWA内で成功表示し、自分宛LINEへ `保存しました` を返さない。相手に届けるお願い・共有等は通常通り通知する。

PWA一覧では連続編集を可能にし、checkbox操作ごとのfull reload/scroll resetを禁止する。

LINE/PWA同時編集、auth、deep-link state restorationは詳細設計で競合戦略を決める。

# 15. イベント・準備

イベント作成時は、種別template + 実際の内容からAIが準備候補を出し、ユーザーが確認して登録する。AIが大量ToDoを勝手に確定しない。

イベント全体の責任者は置かず、個別準備ToDoに担当を持つ。

イベントレベルのLINE通知は毎週定例で送らず、以下の節目/risk時だけ。

- イベント接近
- 今週期限の準備
- 担当未定
- 期限超過
- イベント日変更

複雑なtask dependency DAGは本Baselineでは必須化しない。`待ち / 状況メモ / 次回確認日` 等でまず運用し、独立レビューで不足を評価する。

# 16. Google Calendar

## 16.1 境界

- **Google Calendar:** 家族の時間を押さえる予定
- **おうちノート:** 家庭の作業・準備・お願い・実績

ToDoは基本おうちノートのみ。必要なToDoだけ個別に `カレンダーにも表示` 可能。
LINEのTodayでは両方を統合する。

## 16.2 Google側日時変更

予定日時変更は予定へ反映する。関連準備に影響があればAIが変更候補を出す。予約済み・人が確定した内容を勝手に動かさない。

## 16.3 Google側削除

即削除しない。

- `予定を中止`
- `別日に変更予定`
- `Googleだけから消した`

を確認する。

中止時は未完了準備を不要候補にし、完了実績は残す。別日予定なら `待ち` にして新日程確定後に再配置可能。Googleだけ非表示ならおうちノート予定を維持する。

## 16.4 重複 / 競合

Googleに同一候補があれば、既存予定へlinkするか別追加か確認し、自動二重登録しない。

人が手動確定した内容、夫婦合意、AI/画像解析、Google同期が競合した場合、最後に来た情報を勝手に採用せず差分を見せる。

# 17. 園のお知らせ・コドモン画像連携

## 17.1 目的

園掲示物写真、月間予定表、コドモン等のスクリーンショットから、**予定・共有・準備ToDoまで変換**する。単なるOCRではない。

## 17.2 画像送信

LINEに画像を送ったら軽く内容判定する。

- 園お知らせ / コドモン / 予定表らしい: 解析候補を出す。
- 普通の家族写真: 家庭運営情報の解析提案を出さない。

`追加 → 画像から取り込む` から入った時は解析前提。

## 17.3 子・園・クラス判定

園名、ロゴ、クラス名、画面形式等から自動判定する。

- マサキ / すだちぐみ
- ウタノ / ゆきぐみ
- 別保育園

曖昧な時だけ本人に確認する。

他クラス・他児童の情報は家庭用構造化データへ原則取り込まない。対象か迷う項目だけ確認する。

## 17.4 事実とAI推測

画面上でもデータ上でも分離する。

例:
- `お知らせに記載`: 9/20 食育
- `AIの準備提案`: 前日にエプロン準備

「園が言ったこと」と「AIが先読みしたこと」を混同させない。

## 17.5 園別の確認済みルール

ユーザーが確認・登録した対応関係を、園・子ども単位で確認済みルールとして蓄積できる。

例:
- 食育 → エプロン
- 絵の具 → 汚れてよい服
- プール → 水着セット

AIが一度推測しただけでは確認済みルールへ昇格しない。

## 17.6 複数画像

短時間に連続した複数画像は同じ資料かAIが判定してまとめて解析可能。同園・同クラス・同じ通知の連続ページなら統合候補。別園等なら分ける。

## 17.7 解析確認

対象、日付、予定、持ち物、ToDo等を1画面で確認し、**項目単位で修正**できる。1箇所の誤読で全項目を入力し直させない。

## 17.8 元画像

登録情報に元画像/スクショを出典として紐づけ、夫婦双方が詳細から参照できる。普段のLINEへ画像を再送しない。

一定期間後に元画像だけ整理・削除可能。構造化した予定・ToDo・履歴は残す。重要画像は個別保持可能。

## 17.9 後続通知・競合

新しいお知らせが既存予定を変更・延期・中止している場合、関連する既存予定・準備ToDoまで含めた変更候補を出す。旧情報・旧画像・変更履歴は残す。

手入力確定と画像情報が食い違う場合、最後に読み込んだ情報を自動採用せず、現在確定値と新情報を並べて人が決める。

## 17.10 月間予定表

大量の予定から家庭に影響するものを `登録おすすめ` として優先し、残りは `その他の予定` から確認できる。AIが勝手に捨てない。

優先例: 持ち物、服装指定、保護者対応、時間変更、提出物。

## 17.11 定例 / 特定日例外

`7-8月 毎週火木プール` 等を期間付き定例候補として認識する。AIが勝手に恒久化せず適用期間を確認して登録。

定例の `この日だけ中止/変更` は定例本体を壊さず、その回だけ例外化。関連準備もその回だけ不要/移動候補にする。

## 17.12 提出物 / URL / QR

`9/15までに健康調査票提出` 等は基本 **期限付きToDo**。必要なら準備ToDo候補も出す。Calendarには自動投入しない。

URL/QR/回答先を高確度で読める場合はToDoの `実行先` として紐づける。確度が低い場合は勝手にlink確定しない。

提出・申込みも通常は1tap完了。必要時だけ完了メモ・完了スクショを任意添付できる。日常家事へ証跡UIを常時出さない。

# 18. 1人LINEテストモード

妻を本番LINEユーザーとして追加する前に、1つのLINEトークで双方の流れをテストできること。

例:
1. パパがお願い送信。
2. 同一トークに `🧪 テスト: ママへの通知`。
3. 仮想ママとして `やる / 難しい / その他` を操作。
4. 同一トークに `🧪 テスト: パパへの返答`。

要件:
- 実際のoperatorとsimulated actorを分離して保存する。
- 本番2人運用と同じ業務ロジックを使う。
- test dataを実績分析から除外可能。
- テスト終了後、実ユーザー追加だけで2人運用へ移れる。
- テスト専用の別データモデルを作らない。

# 19. 履歴・振り返り

振り返りはLINEで定期pushしない。PWAの履歴/振り返りの奥に置き、必要ならLINE自然文から呼び出す。

例:
- `今月どれくらいやった？`
- `担当外でやったこと教えて`

最初は個人の完了、担当外サポート、予定外家庭作業、よくやるカテゴリを見せ、必要なら家庭全体へ。

競争ランキングや「どちらが勝った」を避ける。件数は参考値。

# 20. 削除・不要・中止

- **削除:** 登録ミス等、そもそも存在すべきでなかった。
- **今回は不要:** この回だけ不要。
- **中止:** 実在した予定/作業が中止になった。
- **不要になった:** 外部事情等で必要性が消えた。

実績済みのものを削除して過去の事実まで消さない。必要なら訂正履歴で処理する。

# 21. 重複・競合の共通原則

同じ予定・ToDo・共有らしいものを検出しても勝手に統合しない。

必要時だけ:
- `既存を使う`
- `更新する`
- `別件として追加`

を確認する。

人が確定した値とAI/外部同期が競合した場合、**silent overwrite禁止**。

# 23. 実装前の独立レビュー必須論点

1. 通常ケースが本当に少ない操作で済むか。
2. LINE通知が家庭運営の助けではなくnagにならないか。
3. 予定担当・個別合意・claim・実施者・入力者の状態モデルに矛盾がないか。
4. お願いと担当変更、`確認してみる` と `相談する` の状態遷移に穴がないか。
5. `全部やった / 大体やった / 個別で答える` が実績集計を歪めないか。
6. `未入力` を未達として誤集計しないか。
7. 定例ルール変更とfuture overrideの再計算が安全か。
8. Google同期が人の確定情報を破壊しないか。
9. 園画像から事実と推測を安全に分離できるか。
10. マサキ・ウタノが別園であることを誤結合しないか。
11. 画像由来の定例・変更・提出物・URLまで自然に扱えるか。
12. 1人テストモードから2人本番へ無理なく移れるか。
13. 実績が夫婦の圧・競争・恩着せがましさを強めないか。
14. レアケース対応が通常UIに露出しすぎていないか。
15. dependency DAGを本Baselineで必須にしない判断が妥当か。
